# ADR-0026: Credential cryptography uses AWS-LC through aws-lc-rs

- Status: Accepted
- Date: 2026-11-03
- Deciders: @LeeroyHannigan

## Context

ExtendDB stores the secret of every access key and every `AssumeRole` session
encrypted with AES-256-GCM under the catalog encryption key, with the access
key id as additional authenticated data (AAD). Before this decision the code
existed in nine copies: an encrypt function in the server's management API,
and an encrypt and a decrypt function in each of the four storage backends.
The copies differed:

- The PostgreSQL, MongoDB, Cassandra and server copies did not check the key
  length. They passed the key to `Key::from_slice`, which panics on a key that
  is not 32 bytes.
- All four decrypt copies retried without AAD when decryption with the AAD
  failed, so a secret written without AAD opened under any access key id.
  Every release from 0.1.0 to 0.1.14 encrypts with the AAD, so no catalog
  written by a release holds a secret that needs the retry.
- The encryption key was generated by the `aes-gcm` key generator on three
  backends and by `rand` on MongoDB.

Signature Version 4 (SigV4) verification computed SHA-256 and HMAC-SHA256 with
the `sha2` and `hmac` crates and compared signatures with a hand-written loop.

AWS-LC is already in every ExtendDB binary. ExtendDB installs the
`rustls::crypto::aws_lc_rs` provider for its TLS server and clients, and sqlx
connects to PostgreSQL with `tls-rustls-aws-lc-rs`.

## Options Considered

1. **Keep the RustCrypto crates and merge the copies.** One module for secret
   encryption, still on `aes-gcm`, `hmac` and `sha2`. The credential path and
   the TLS path keep using different cryptography libraries.
2. **Move the credential path onto aws-lc-rs.** One module for secret
   encryption, and the SigV4 SHA-256, HMAC-SHA256 and signature compare, all
   from AWS-LC, the library the TLS provider already uses.
3. **Move the credential path onto ring.** ring has the same primitives and is
   in `Cargo.lock`, but of the backend builds only the MongoDB one links it.
   ExtendDB does not use ring as its TLS provider, and ring has no Federal
   Information Processing Standards (FIPS) module.

## Decision

Secret encryption, encryption key generation, and the SigV4 SHA-256,
HMAC-SHA256 and signature compare use aws-lc-rs (Option 2).

## Rationale

- `extenddb_storage::secret_cipher` replaces the nine copies, so every backend
  checks the key length the same way.
  `extenddb_storage::bootstrapper::helpers::generate_encryption_key` is the one
  key generator.
- `RandomizedNonceKey` draws a fresh 96-bit nonce for each seal, so no caller
  builds a nonce.
- Signatures are compared with the AWS-LC `CRYPTO_memcmp`. The hand-written
  Rust loop was constant time only if the compiler emitted it that way.
- aws-lc-rs 1.18 is already linked into every binary for TLS, with the
  features this change enables (`aws-lc-sys` and `prebuilt-nasm`). Eight
  crates leave `Cargo.lock`: `aead`, `aes`, `aes-gcm`, `ctr`, `ghash`,
  `opaque-debug`, `polyval` and `universal-hash`.
- aws-lc-rs has a `fips` feature that builds the AWS-LC-FIPS module through
  `aws-lc-fips-sys`. For aws-lc-rs 1.18 that module is AWS-LC-FIPS 4.x, which
  the aws-lc-rs documentation describes as submitted to the National Institute
  of Standards and Technology (NIST) for certification. A FIPS build also needs CMake and Go. This decision does not
  turn the feature on.

## Consequences

- The stored format does not change: `nonce(12) || ciphertext || tag(16)`, with
  the access key id as AAD. Unit tests decrypt a secret from the 0.1.14
  release fixture and a secret written by the `aes-gcm` code.
- A secret written without AAD no longer decrypts, and an empty AAD is
  refused. No release wrote such a secret.
- `sha2` stays for principal ids in `crates/auth/src/policy/principal_id.rs`,
  and `hmac` stays for transaction tokens in `crates/engine`. Neither is on the
  credential path.
- aws-lc-rs compiles C and assembly. Every binary already did this for rustls,
  so the toolchain requirement is unchanged. A build of `extenddb-storage`,
  `extenddb-auth`, or the Cassandra or MongoDB backend crate on its own now
  compiles `aws-lc-sys` as well.
- The encryption key is still stored in the catalog. Moving it out of the
  catalog and adding rotation needs an RFC.
