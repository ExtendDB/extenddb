# Design Spec: Off-Host Backup and Restore for ExtendDB

Status: Draft for maintainer review. Written 2026-09-10 against main `4fd2c5f8`; revised 2026-10-12 and 2026-10-13 against main `9f43d03`, PR 0 = #384, and the open series PR 2 = #396 (this document), PR 3 = #393 (supersedes #336), PR 4 = #394 (supersedes #337), PR 5 = #395; PR 1 is #335 rebased (see the revision log at the end). Target: v1.0.

## Summary

ExtendDB backups today are rows inside the same database that holds the data, in a shape private to each storage backend. This spec replaces that with a single portable backup format written to a configured backup store, either a local directory or an S3 bucket, driven by the engine rather than by each backend. The DynamoDB API contract does not change: CreateBackup, DescribeBackup, ListBackups, DeleteBackup, and RestoreTableFromBackup keep their request and response shapes. Backends gain one new obligation, a consistent snapshot iterator over a table, and lose the obligation to implement backup storage themselves. The format is the DynamoDB S3 export layout plus one ExtendDB manifest, so a backup restores into any backend, imports into Amazon DynamoDB with ImportTable, and a DynamoDB export restores into ExtendDB.

The spec also settles point-in-time recovery for v1: unsupported, reported honestly, with the format designed so a later change-log archive can add it.

## Motivation

The v1 readiness analysis (v1gaps-backup-dr.md, v1gaps-data-integrity.md) found:

1. Every backup shares the failure domain of its data. Host, disk, or database loss takes the backups with it. No off-host mechanism exists.
2. PostgreSQL backup dropped the sort key of every composite-key table because it checked for a column literally named sk; restore then wedged the table in CREATING. Closed by #384 (PR 0 of this series).
3. SQLite and PostgreSQL restore dropped GSIs, LSIs, throughput, table class, and encryption settings; SQLite silently dropped vector indexes (F-19). Closed by #384 for the in-catalog path (vector indexes are refused rather than restored). The three backends still store three different shapes.
4. Backups cannot cross backends or versions because each backend stores its own shape.
5. Point-in-time recovery reports ENABLED with a 35-day window and can never restore.
6. Export is not a consistent snapshot (issue #57, PR #80 open).
7. Loss of the catalog destroys the ability to find or restore backups.

Three separate per-backend fixes would leave items 1, 4, and 7 open. One engine-owned path with a portable format closes all seven.

## Goals

- Backups survive loss of the ExtendDB host and of the backend database when the store is S3.
- One backup format for all backends; a backup taken on any backend restores on any backend.
- Restore reproduces what Amazon DynamoDB reproduces: items, key schema, attribute definitions, GSIs, LSIs, billing mode and throughput, table class, and the vector index set. Streams settings, TTL, tags, and PITR settings are not restored, matching DynamoDB.
- A backup is a consistent snapshot of the table as of one instant.
- CreateBackup and RestoreTableFromBackup are asynchronous with DynamoDB status transitions; a crash mid-operation leaves state a startup reconciler resolves.
- The catalog can be rebuilt from the store.
- Existing API request and response shapes are unchanged.

## Non-goals

- Point-in-time recovery. Phase 3 describes how the format supports it later.
- Cross-account restore. The backup ARN account must equal the caller account, as today. `backup sync` can adopt a bucket written by another instance, but every adopted backup stays under the account its ARN names; no request crosses accounts.
- Backup encryption inside ExtendDB. Encryption at rest is the store's job (S3 SSE-S3 or SSE-KMS, filesystem encryption). The spec states this in the deployment guide.
- Scheduled backups. Operators schedule CreateBackup externally in v1. Phase 3 adds a scheduler.
- Multi-instance coordination beyond the per-job claims in 5.1. Two instances may run jobs concurrently; they may not both own one job. There is no single-instance lease on PostgreSQL or MongoDB (readiness item P0-7 is open) and this design does not add one.

## Detailed design

### 1. Backup format

A backup is a prefix in the store containing:

```
<root>/<account_id>/<table_name>/<backup_id>/
  extenddb-manifest.json          written last; its presence means the backup is complete
  extenddb-manifest.sha256        sha256 of the manifest's stored bytes; written before the manifest
  manifest-summary.json           DynamoDB export summary shape
  manifest-files.json             DynamoDB export file list shape, one JSON object per line
  data/<part>.json.gz             DynamoDB JSON, one {"Item": {...}} per line, gzip level 6
```

Write order: data files, `manifest-files.json`, `manifest-summary.json`, `extenddb-manifest.sha256`, then `extenddb-manifest.json`. The manifest's presence is the commit record. The sidecar is in `sha256sum` format (`<hex>  extenddb-manifest.json`), so `sha256sum -c` verifies a backup from a shell; the reader accepts a bare digest too. A prefix with a manifest whose sidecar is missing or does not match is corrupt and is refused by restore and skipped by `backup sync`.

`manifest-summary.json` and `manifest-files.json` follow the shapes Amazon DynamoDB writes for ExportTableToPointInTime with exportFormat DYNAMODB_JSON, so the `data/` prefix is a valid ImportTable source for the real service. (ExtendDB's own ImportTable reads a single local file today; reading a store prefix is Phase 2.) `manifest-files.json` carries per-file `itemCount`, `md5Checksum`, `etag` (omitted on a filesystem store, which has none) and `dataFileS3Key`. The service writes `dataFileS3Key` as the object's full bucket key (`AWSDynamoDB/<export id>/data/<file>`); ExtendDB does the same, `<store prefix><account>/<table>/<backup id>/data/<file>`. ImportTable does not read this manifest, it lists the prefix it is given, so the field is informational.

`extenddb-manifest.json` is the ExtendDB extension and the commit record:

```json
{
  "format_version": 1,
  "backup_arn": "arn:aws:dynamodb:<region>:<account>:table/<table>/backup/<id>",
  "backup_name": "...",
  "backup_creation_date_time": 1757500000.123,
  "backup_size_bytes": 123456,
  "source_backend": "postgres",
  "source_extenddb_version": "0.1.11",
  "snapshot": { "kind": "postgres_repeatable_read", "marker": "..." },
  "item_order": "key_ordered",
  "source_table": {
    "table_name": "...", "table_id": "...", "table_arn": "...",
    "table_creation_date_time": 1757400000.0,
    "key_schema": [...], "attribute_definitions": [...],
    "billing_mode": "PROVISIONED", "provisioned_throughput": {...}, "on_demand_throughput": null,
    "table_class": "STANDARD", "sse_specification": {...},
    "global_secondary_indexes": [...], "local_secondary_indexes": [...],
    "vector_indexes": [...],
    "item_count": 100000, "table_size_bytes": 123456
  },
  "data_files": [
    { "key": "data/000001.json.gz", "item_count": 50000, "sha256": "...", "md5": "...",
      "bytes": 61728, "uncompressed_bytes": 15900000,
      "key_range": { "first": { "pk": {"S": "a"}, "sk": {"N": "1"} }, "last": { ... } } }
  ]
}
```

Field rules (`crates/core/src/backup_format/manifest.rs` is the authority; `crates/core/testdata/extenddb-manifest/v1.json` is the frozen byte-for-byte shape, and a test fails if any reused wire type changes it):
- Optional `source_table` members are always present, `null` when absent, for human readers and non-Rust tools. A reader accepts a missing member as `null`; "the writer did not know this field" is signalled by `format_version`, not by absence. `global_secondary_indexes` and `local_secondary_indexes` are plain arrays, empty when the table has none. Members of the nested `DynamoDB` wire types keep that API's own conventions (optional members omitted when absent, `PascalCase` names).
- The manifest's `backup_arn` is parsed with `BackupArn` on load and is the backup's identity: `source_table.table_name` must equal the ARN's table and `source_table.table_arn` must be a table ARN for the same account and table (its region is not compared; it is recorded at table creation and the backup ARN carries the region configured at backup time). `backup_size_bytes` must equal the sum of the data files' `bytes`; a data file key may appear once.
- `vector_indexes` has three states: `null`, the source backend has no vector support (a target with vector support restores the table without vector indexes); `[]`, the source supports vector search and the table had none; non-empty, a target without vector support refuses the restore. Entries are creation specifications, not runtime descriptions.
- `item_order` is `key_ordered` or `unordered`. Key order is defined once, in `extenddb_core::backup_format::key_order`: hash key by the text encoding the storage layer keys rows with (`S` as is, `N` as its normalized decimal string, `B` as base64), compared bytewise, so a number hash key sorts as text (`"10"` before `"9"`); range key `S` and `B` bytewise, `N` by numeric value. `hash_key_text` takes the `N` string as given and assumes it is normalized; every `N` key in a `key_range` must be a valid DynamoDB number in normalized form (the manifest parser refuses `1E200`, `1_000`, `5.0`), and the restore normalizes every item's `N` values with `validate_and_normalize_number` before computing key text or comparing (5.3 step 5), so `"5"` and `"5.0"` cannot become two rows. The SQL backends produce this order from their primary key columns, SQLite with its `BINARY` collation and the order-preserving `sk_n` encoding (a `storage-sqlite` test binds that encoding to the comparator), PostgreSQL only with `COLLATE "C"` on `pk` and `sk_s` in the `ORDER BY` (tables created before the key columns were declared `COLLATE "C"` keep the database collation); the storage layer's `pk_to_text` binds the same encoding function and the restore's checks bind the same comparator, so for the hash key writer, reader and row key agree by construction and for the range key the backend tests hold the agreement. `key_ordered` means items ascend strictly in that order within each file and from one file to the next, every data file carries a `key_range` whose `first` and `last` are key-only items of the schema's shape, and the ranges do not overlap; the manifest parser enforces the range rules and the restore enforces strict ascent within each file while streaming it, so a duplicate key anywhere fails the restore. Only hash-only and single-range-key tables can be ordered; PostgreSQL and SQLite sources write `key_ordered` for those, MongoDB sources and multi-part-key tables write `unordered`. SQLite inserts into a fresh table 3 to 4 times faster when rows arrive in key order (libsqlite 3.46 bundled, 1M synthetic 318-byte items, localhost; ratio only); a restore may exploit the flag and must produce the same table either way.
- `backup_creation_date_time` is the instant the snapshot pinned: it is recorded when `open_table_snapshot` returns in the CreateBackup request (5.1 step 2), after any wait behind an in-flight UpdateTable, so it is the time the data files represent.
- There is no checksum field inside the manifest. The sidecar holds the sha256 of the stored bytes. An earlier draft hashed a re-serialized struct with the field blanked, which tied the digest to one JSON library's float formatting and field order; nothing but a Rust reader using the same serde version could have verified it.

Rules:
- The `data/` prefix contains only data files, so ImportTable against that prefix never sees a manifest.
- `extenddb-manifest.json` is written after every data file and both DynamoDB manifests succeed. A prefix without it is an incomplete backup and is invisible to ListBackups after `backup sync`.
- `format_version` is checked before anything else is parsed, so a document from another version is reported as unsupported rather than as a parse error about a member this build does not know; any version other than the one this build writes is refused. Adding an optional field does not require a version bump (the integrity check is over stored bytes and readers tolerate unknown fields); changing the meaning of a field, or adding one a reader must understand to restore correctly, does.
- A target without vector support refuses a manifest with a non-empty `vector_indexes` with the existing message ("restoring a table with vector indexes is not supported by this storage backend") rather than dropping them. This closes F-19 uniformly.
- A restore rejects a backup whose data files contain the same primary key twice, across files as well as within one. For key-ordered backups the manifest's `key_range` check rejects overlap before any file is downloaded and the restore verifies strict ascent within each file; for unordered backups duplicate detection is the target's primary key: a plain `INSERT` on PostgreSQL and SQLite fails on a duplicate and so does MongoDB's `_id` unique index (E11000). After a MongoDB resume, where E11000 is suppressed for the one file being re-applied (5.3 step 5), the job checks that `countDocuments` after that file equals the cumulative `item_count` of the files applied so far; a shortfall is a duplicate between that file and an earlier one and fails the restore. No in-memory key set is kept, so restore memory does not grow with the table (section 7). Duplicate keys cannot come from a clean snapshot; they indicate a corrupt or forged backup, and silently keeping the last writer would make the restored table depend on file order.
- Numbers are DynamoDB JSON strings, so the 38-digit precision survives the file. A restore into MongoDB of a value beyond Decimal128's 34 digits fails item validation with ValidationException and the restore reports FAILED (see 5.3); it never rounds.

### 2. Backup store abstraction

New crate `crates/backup-store` with one trait and two implementations:

```rust
pub trait BackupStore: Send + Sync {
    fn put(&self, key: &str, body: ByteStream) -> BoxFuture<Result<ObjectMeta, StoreError>>;
    fn get(&self, key: &str) -> BoxFuture<Result<ByteStream, StoreError>>;
    fn head(&self, key: &str) -> BoxFuture<Result<Option<ObjectMeta>, StoreError>>;
    fn list(&self, prefix: &str) -> BoxStream<Result<ObjectMeta, StoreError>>;
    fn delete_prefix(&self, prefix: &str) -> BoxFuture<Result<u64, StoreError>>;
    fn validate(&self) -> BoxFuture<Result<(), StoreError>>;
}
```

`put` returns the stored object's size and, where the store has one, its ETag (unquoted; a multipart ETag is not an MD5), so the manifest writer records both without a second request. `validate` is the startup check (section 7). The signatures above elide the explicit lifetimes the crate uses (`fn put<'a>(&'a self, key: &'a str, ...) -> BoxFuture<'a, ...>`); `extenddb_backup_store::open(&BackupStoreConfig)` is the constructor the server calls.

- `FilesystemStore`: root directory from config. Keys map to paths under the root; every component is resolved without following symlinks, and `put`, `get` and `head` refuse any symlink in a key's path, inside or outside the root (`list` and `delete_prefix` skip symlinks: a listing is not an access through the link, deletion removes a link found below the prefix without following it, and a symlink at the prefix path itself is treated as nothing there). Those checks are path-based and can be raced by a process that can reach the tree, so the store requires that nobody but the owner can, and enforces it: `open` and `validate` refuse a root that grants any permission to group or others or is owned by another uid, and refuse a root whose ancestor directory is owned by a third user (neither the server's uid nor root) or is writable by others without the sticky bit (such an ancestor lets another user rename the root away and plant a symlink at its path); every operation, `list` and `delete_prefix` included, re-checks the root and refuses any existing directory it descends into that fails the same owner-only rule; directories are created `0700` and objects `0600` at creation rather than fixed up afterwards; every refusal names the path and the `chown`/`chmod` to run. Consequence for operators: a pickup agent (rsync, restic, borg) cannot read the tree as a member of the server's group and runs as the server's user or as root; a root under a directory owned by a storage administrator or an NFS mount owned by `nobody` is refused at startup. A bind mount or a filesystem without Unix permission semantics is outside what the store can observe; the deployment guide names those. Writes go to a temporary sibling, `fsync` the file, rename into place and `fsync` the directory, so a crash never leaves a truncated file under its final name and an acknowledged put survives power loss; a failed put removes the temporary, any directories it created, and the renamed file if the directory `fsync` fails after the rename, so a failed put leaves nothing observable under the key, as on S3. `delete_prefix` treats an object that vanished between listing and removal as deleted, so two reconcilers retrying the same tombstone do not fail each other.
- `S3Store`: bucket, prefix, region, optional endpoint and path-style flag for S3-compatible stores, credentials from the standard AWS SDK chain (environment, shared config, IMDS, IRSA, container credentials). Uploads over `upload_part_size_bytes` use multipart (S3's 10,000-part limit caps one object at about 78 GiB at the 8 MiB default); failed multipart uploads are aborted. `validate` distinguishes a missing bucket (404), a denied one (403) and one in another region (301, naming the region from `x-amz-bucket-region`). Dependency: the official `aws-sdk-s3` crate, chosen over `object_store` because it inherits the SDK credential chain, IRSA support, and retry behavior that operators already configure for other AWS tooling. The dependency adds 43 crates to the licenses check (Apache-2.0 / MIT); the notice files are regenerated in the store PR.

Both implementations are exercised by the same conformance test module in the crate. Every S3 test takes its endpoint from one helper, which fails rather than skips when `EXTENDDB_TEST_S3_REQUIRED` is set and no endpoint is configured; CI sets it, so no S3 test can be skipped there through a private path. The endpoint is moto in server mode, a pip package pinned in the workflow; MinIO was the original choice but the project archived in April 2026 and publishes no images.

Authority: `crates/backup-store` (PR 3, #393); its README states the behaviour above and this section follows it.

### 3. Storage trait changes

`BackupEngine` on the storage trait is reduced to what only a backend can do. Removed: `create_backup`, `describe_backup`, `list_backups`, `delete_backup`, `restore_table_from_backup`, `restore_table_to_point_in_time`. The engine owns those now. Added:

```rust
pub struct TableSnapshot {
    pub description: TableDescription,   // the table as DescribeTable reported it at the snapshot instant
    pub info: SnapshotInfo,              // { kind, marker }
    pub key_ordered: bool,               // items arrive in base-table key order
    pub items: BoxStream<'static, Result<Item, StorageError>>,  // owns the transaction/session
}

pub trait SnapshotEngine: Send + Sync {
    fn open_table_snapshot(&self, account_id: &str, table_name: &str)
        -> BoxFuture<Result<TableSnapshot, StorageError>>;
}
```

The definition and the items are returned by one operation because they must describe one instant and on PostgreSQL they live in different databases. An earlier draft returned items only and left the definition to a separate DescribeTable; a GSI added or the table deleted between the two calls would have produced a manifest that did not match its data files. Indexes are reported in whatever lifecycle status they had at the snapshot, except that an index being deleted is dropped (one shared rule, `extenddb_storage::snapshot::drop_deleting_indexes`): a restore recreates the indexes the description lists and builds them from the items, so a `CREATING` index comes back complete, while an index left out of the description would not come back at all; an index the user had removed must not. This is the rule the in-catalog backup already applies (it records every index row and none of its build state). `SnapshotInfo { kind, marker }` is the manifest's `snapshot` member; PR 5 lands it as a struct in `extenddb-storage`, and once PR 4 is merged it becomes `pub use extenddb_core::backup_format::SnapshotDescriptor` so there is one definition (`extenddb-storage` already depends on `backup_format` for `hash_key_text`); `kind` is one of `postgres_repeatable_read`, `sqlite_wal_read_transaction`, `mongodb_snapshot_read_concern`, and `marker` is `pg_current_snapshot()` text, empty, or the cluster time `<seconds>:<increment>` respectively. `key_ordered` is true only for hash-only and single-range-key tables on the SQL backends (`extenddb_storage::snapshot::key_schema_is_orderable`); multi-part keys and MongoDB stream unordered. `StorageError::SnapshotExpired` is returned from the stream when the backend discarded the snapshot before it was drained (PostgreSQL SQLSTATE 40001 from a hot standby and 72000 `snapshot_too_old` on a primary with `old_snapshot_threshold` set; MongoDB code 239 `SnapshotTooOld` and 246 `SnapshotUnavailable`); the holder restarts from the beginning and never combines rows from two snapshots. The stream owns a pooled connection whose drop schedules its return on the Tokio runtime, so a `TableSnapshot` is dropped inside the runtime that opened it.

Per-backend implementation (merged as PR 5 of this series):
- PostgreSQL: the `tables` row is held `FOR SHARE` from the definition read until the data transaction has pinned its snapshot; UpdateTable and DeleteTable take that row `FOR UPDATE`, so neither commits in the gap. Background workers that flip an index's status (a vector build finishing) do not take the row lock; an index that becomes ACTIVE in the gap is reported `CREATING`, which the restore builds from the items like any other. The data transaction is `REPEATABLE READ READ ONLY` with `ACCESS SHARE` on the relation (blocks DROP, not DML); `SELECT pg_current_snapshot()` pins it and its text is the marker. Items stream through a server-side cursor, `FETCH 1000` per round trip (localhost PostgreSQL 16, 318-byte items: 1000 and 10000 read a million rows in the same time; over a 1 ms network link the larger fetch would save about a second per million rows, and the size is a constant, not a knob), `ORDER BY pk COLLATE "C", <sort column>` so the order is the format's regardless of the column's declared collation. The transaction holds one connection from the data pool for the job's duration; section 7 sizes the pool for it. It blocks no writer but retains every dead tuple written during the backup (same host: 200k concurrent PutItem calls of 318-byte items, each its own transaction, kept 110 MB until the snapshot closed); the deployment guide states this and the worker reports snapshot age. Opening waits behind an in-flight UpdateTable or DeleteTable on the table; otherwise it is milliseconds.
- SQLite: one deferred read transaction covers catalog and data; its first read pins the WAL snapshot and every catalog and data read that follows comes from it, so no lock is taken and writers never wait on a snapshot being opened. The WAL cannot checkpoint past the reader, so it grows by the write volume during the backup (same host, libsqlite 3.46 bundled: 899 MB for 200k PutItem calls of 318-byte items, each its own transaction). Items page through row-value keyset pagination on the primary key index. In-memory databases are pinned to one connection and refuse snapshots with `Unsupported`; CreateBackup on `sqlite-memory` returns that error.
- MongoDB: a session started with `snapshot: true` reads the `tables` document, the `indexes` documents and the base collection at one cluster time, which is the marker. Every read sets `readConcern: snapshot` explicitly, because the driver only inserts that level when the operation has none and a connection string with `readConcernLevel=` would otherwise turn the whole session into ordinary reads with nothing failing; a session that reports no snapshot time after its first read fails the open. Snapshot history is bounded server-side (`minSnapshotHistoryWindowInSeconds`, default 300), so a slow upload of a large collection can fail with SnapshotTooOld. Mitigation in v1: the worker reads the collection in batches under the snapshot session while buffering to the store; if the cursor fails with SnapshotTooOld the backup fails and the operator raises the server window (documented). Alternative considered: a server-side `$out` copy to a scratch collection, then a plain stream from the copy; rejected for v1 because it doubles storage per backup and the existing restore path already uses `$out` for a different reason. Revisit if operators hit the window.
- Cassandra: out of scope for this spec. The backend is Experimental at v1 and implements the trait when it graduates.

Authority: `crates/storage/src/snapshot.rs` and the three `snapshot_engine.rs` files (PR 5, #395); the module docs there carry the per-backend mechanism and this section follows them.

The continuous-backups methods (describe and update) and the point-in-time restore method leave the trait in the PITR PR; the engine serves those three operations itself (section 6).

Existing in-catalog backup tables (`backups`, `backup_items`, `backup_definitions`, `table_restores` on PostgreSQL and SQLite; the `backups` collection and `_backup_<backup_id>` collections on MongoDB, as PR #384 leaves them) stay readable for one minor release. `LegacyBackupReader` is a trait in `extenddb-storage` with `describe`, `list`, `restore` and `delete`; each backend implements it with a frozen copy of its #384 code (not calls through trait methods later PRs remove), and the engine holds `Option<Arc<dyn LegacyBackupReader>>`. Describe, List, Delete and Restore on the engine consult the new catalog index first and fall back to the reader; List returns legacy rows after new rows in the same (`created_at`, `backup_id`) order, and the pagination cursor records which source it is in. `create_backup` never writes the legacy shape again. PR 14 removes the trait. The upgrade manual tells operators to restore or delete legacy backups before the release that removes the reader.

### 4. Catalog index

The engine keeps a `backups` catalog row per backup as the fast index for Describe and List, and as the state machine record:

```
backup_id         <epoch millis>-<8 lowercase hex>, generated once in the engine
account_id, table_name, backup_arn, backup_name,
status            CREATING | AVAILABLE | DELETING | DELETED | FAILED
store_kind        filesystem | s3
store_root        the configured root at creation time
store_key_prefix  <account>/<table>/<backup_id>/
size_bytes, item_count, created_at, completed_at, failure_reason,
source_table_details_json   the manifest's source_table object, verbatim
owner_generation  fencing token of the job that holds the row (section 5.1)
heartbeat_at      last progress write by that job
```

`source_table_details_json` is written at CREATING from the snapshot's description through the serializer the manifest writer uses, and rewritten from the manifest's `source_table` member in the AVAILABLE update, so an AVAILABLE row equals the manifest byte for byte; the API's `SourceTableDetails` and `SourceTableFeatureDetails` are derived from it by one function in the engine, so the definition exists in one encoding. The backup id has one format on every backend (today PostgreSQL writes `<millis>-<hex>` and MongoDB a UUID; PR 6 unifies them in the engine).

Status mapping to the API: CREATING and AVAILABLE as themselves; DELETING is reported as DELETED (a client retrying DeleteBackup sees the terminal status); DELETED and FAILED rows are not described (BackupNotFoundException, which is what the live service returns for a deleted backup; only DeleteBackup's own response carries DELETED) and not listed. DynamoDB has no FAILED status, and reporting a failed creation as DELETED would imply a backup that existed; a creation that failed never existed. FAILED and DELETED rows are tombstones the reconciler owns: for a FAILED row it retries `delete_prefix` while the prefix lists non-empty, and it removes either kind once the prefix is empty and the row is older than `failed_row_retention_secs` (default 7 days). `extenddb backup list --failed` prints FAILED rows with their `failure_reason`.

The engine keeps a `restore_jobs` row per restore in the same catalog:

```
table_id, account_id, table_name, backup_arn,
status            RUNNING | FAILED | DONE
owner_generation, heartbeat_at      the same claim as a backup job (5.1 step 3), keyed `restore:<account>/<table>`
spool_host        the host whose spool holds the downloaded files (5.3 step 3)
failure_reason, created_at, completed_at
```

It ships in PR 6's catalog migration next to `backups`. The per-file progress of a PostgreSQL restore is not in it; that lives in the data database (5.3 step 5). FAILED and DONE restore rows are removed by the reconciler after `failed_row_retention_secs`.

The store is the source of truth; the row is a cache. `extenddb backup sync` lists the root, treats each first-level component as an account id (validated with `BackupArn`'s rule; the reserved `changelog` component is skipped), lists only to the depth `<account>/<table>/<backup_id>/`, reads every `extenddb-manifest.sha256` and `extenddb-manifest.json` pair, and inserts an AVAILABLE row for each prefix that has a verified manifest and no row. Sync considers only rows whose `store_kind` and `store_root` equal the configured store; rows for another store are reported, not touched (`backup sync --forget-store <root>` is the explicit opt-in to mark them DELETED). Within the configured store, sync marks AVAILABLE rows whose prefix no longer holds a manifest as DELETED, and never modifies CREATING, DELETING or FAILED rows nor adopts their prefixes. It never adopts a prefix without a manifest or whose sidecar does not match. Before adopting, sync parses the manifest's `backup_arn` with the one `BackupArn` type in `extenddb-core` and requires the parsed account, table and backup id to equal the listed path components and the `source_table` identity; a mismatch is logged and skipped. Foreign region or partition in an adopted ARN is accepted and logged; requests check only the account. This is the recovery path when the catalog is lost and the store survives, and it is how a fresh ExtendDB adopts a bucket of backups from another instance. Describe of a row whose `store_root` differs from the configured one returns the row and logs a warning; Restore of such a row returns a ValidationException naming the row's store root.

Authority: the catalog migration PR 6 adds (PostgreSQL 005, SQLite schema, the MongoDB `backups` and `restore_jobs` collections) and the engine's `backup` module; this section is the specification they implement.

Trust boundary of sync: a principal that can write under an account's prefix can forge a backup for that account. Checksums do not help, they are forgeable by the same principal. The deployment guide states that write access to an account's prefix is backup-administrator authority for that account, and gives per-account IAM prefix policies. A server-side MAC over manifests is not in v1; if hostile writers with bucket access are in scope for a deployment, the operator restricts write access rather than relying on ExtendDB to detect forgeries.

The ARN encodes partition, region, account, table, and backup id, and the key prefix is derived from account, table and id deterministically by `BackupArn::store_prefix`, so `describe_backup(arn)` works from the store alone after a sync. The engine, the writer and sync all parse and format ARNs through that one type (partition-aware: `aws`, `aws-cn`, `aws-us-gov`); the engine's earlier colon-field account check is replaced by it.

### 5. Operations

#### 5.1 CreateBackup

1. Validate table exists and is ACTIVE for the account (existing checks). Reserve a job slot: `max_concurrent_jobs` is a semaphore the request `try_acquire`s, not a count of rows, and the permit lives with the job; if none is free return `LimitExceededException` (DynamoDB's answer for too many concurrent backups) before opening anything, because a queued snapshot would hold a PostgreSQL transaction or a MongoDB snapshot session (whose 300 s history window starts at open) while it waited. RestoreTableFromBackup takes a permit from the same semaphore and returns the same error when none is free (5.3 step 1).
2. Generate the backup id and the owner generation, take the PostgreSQL advisory lock where that is the claim (step 3), and open the table snapshot (`SnapshotEngine::open_table_snapshot`) in the request. The open is a BEGIN plus the catalog reads, milliseconds unless an UpdateTable or DeleteTable on the table is in flight, in which case it waits for it (no timeout: the wait is bounded by that operation's own duration, and a client that wants a bound sets its request timeout). It pins the instant the backup represents to the request, which is what DynamoDB promises ("the backup contains all data as of the request time, within seconds"). Insert the catalog row with status CREATING, the backup id, `backup_creation_date_time` = the instant the open returned, `owner_generation`, `heartbeat_at` = the database's `now()`, and `source_table_details_json` taken from the snapshot's description; return `BackupDetails` with BackupStatus CREATING. If the row insert fails the snapshot is dropped, the advisory lock released, the permit returned, and nothing was written.
3. The claim. There is no single-instance lease on PostgreSQL or MongoDB, so each job holds a claim that both excludes a second owner and lets a successor detect a dead one. Every backend sets `owner_generation` (a fresh random value) at claim time, and every catalog write by the job is `WHERE owner_generation = $gen`, so a job that lost its claim cannot publish over a successor's work. What the claim is differs per backend. PostgreSQL: `pg_try_advisory_lock(hashtextextended('backup:' || backup_id, EXTENDDB_LOCK_SEED))` on a dedicated, non-pooled connection to the catalog database (outside `pool_size`; it counts against the server's `max_connections`), taken before the row exists and held for the job's life; the seed is the one constant #384's restore lock already uses (`RESTORE_LOCK_SEED`, renamed and shared so there is one lock key space). The job writes its heartbeats through that same connection, so a managed server dropping the idle session (RDS Proxy, PgBouncer, `idle_session_timeout`) surfaces as a failed heartbeat and the job aborts instead of continuing unowned. MongoDB: the row is the claim; the insert with `owner_generation` and `heartbeat_at = $$NOW` creates it owned, so no row ever exists unowned, and each heartbeat is `update_one({_id, owner_generation: $gen}, {$set: {heartbeat_at: $$NOW}})`; a heartbeat that matches no document means the claim was lost and the job aborts without further store writes. SQLite: one process, so the claim is an in-process slot and a restart is proof of death. Staleness is always measured on the database's clock (`heartbeat_at < now() - interval` on PostgreSQL, `$expr` against `$$NOW` on MongoDB), never on an application host's. A reconciler may claim a row whose heartbeat is older than `stale_job_after_secs` in order to resolve it (step 6); it never continues the upload. The snapshot and the claim connection are handed to the backup worker over an in-process channel; the worker is a task in `crates/server/src/workers.rs`, spawned with the server's cancellation token and retained handle like the existing workers.
4. The job: stream items from the snapshot into gzip data files of at most `data_file_target_bytes` (default 64 MiB uncompressed) through `DataFileEncoder`, which hashes the compressed bytes as they leave the compressor and refuses further writes after a sink error (the file is discarded and restarted from its first item). Compression runs on a blocking thread (`spawn_blocking`) so a backup does not starve request handling. Each file's key range is recorded when the snapshot is key-ordered. Read, compress and upload overlap through bounded channels. Memory per job is `upload_part_size_bytes * max_concurrent_uploads` for the upload, the channel bounds, and the gzip window; it does not depend on `data_file_target_bytes`, because the encoder streams into the multipart upload and never holds a whole file (section 7 states the formula next to the knobs). The heartbeat is written on a timer (`heartbeat_interval_secs`, default 30) for as long as the job task is alive, through the claim connection on PostgreSQL, independent of upload progress, so a slow link cannot make a live job look dead; a heartbeat that fails (connection dropped on PostgreSQL, no document matched on MongoDB) aborts the job without further store writes. `stale_job_after_secs` must exceed several heartbeat intervals; startup refuses a value under `3 * heartbeat_interval_secs`. After the last file: write `manifest-files.json`, `manifest-summary.json`, `extenddb-manifest.sha256`; re-check the claim (PostgreSQL: the lock connection is alive; MongoDB: the generation still matches); then write `extenddb-manifest.json` and update the row to AVAILABLE with size and count (conditional on the generation). Store writes are not fenced by the generation; the re-check narrows the window in which a fenced-out job can still write a manifest, and the FAILED tombstone (section 4) closes what remains: sync never adopts a prefix whose row is FAILED, and the reconciler never deletes a prefix while the row's `heartbeat_at` is younger than `stale_job_after_secs` on the catalog database's clock, so a late manifest from a fenced-out job lands under a tombstone that sync will not adopt.
5. On any failure, including `SnapshotExpired`: set the row FAILED with the reason (conditional on the generation), then abort in-flight multipart uploads and `delete_prefix` the partial backup; if the delete fails the reconciler retries it (section 4). A backup never resumes from a cursor position: rows read under a new snapshot cannot be combined with rows read under the old one, so a lost snapshot means a new CreateBackup. DescribeBackup returns BackupNotFound; ListBackups omits it. `backup_jobs_total{outcome="failed"}` increments. Log at error level with the request id.
6. Shutdown: the snapshot lives in the process and dies with it, so a cancelled job can never complete. On cancellation the worker runs step 5 with reason `shutdown` within the drain window (aborting uploads and deleting the prefix are bounded work). If the catalog is unreachable it leaves the row CREATING for the reconciler; if only the store is unreachable the row is FAILED and the reconciler deletes the prefix later. `backup_jobs_total{outcome="cancelled"}` increments. Crash: on startup and every reconciler cycle, a CREATING row is resolved when its owner is dead. SQLite: every CREATING row at startup is dead (one process). PostgreSQL: a free advisory lock means the owner is dead. MongoDB: `heartbeat_at` older than `stale_job_after_secs` (default 3600) on the server's clock. The reconciler takes the claim with a fresh `owner_generation`, which fences the dead job's generation out, and writes the status immediately: AVAILABLE if a complete, verified manifest exists in the store, else FAILED with reason `owner_dead`; both writes are additionally conditioned on `status = CREATING`, so a fenced-out job that is somehow still alive cannot flip the reconciler's FAILED back. The prefix of a FAILED row is deleted by the reconciler only once `heartbeat_at` is older than `stale_job_after_secs`, which is the delay step 4 relies on; on PostgreSQL and SQLite that delay follows the resolution, on MongoDB it has already elapsed. A restarted process cannot finish a CREATING backup; AVAILABLE from an existing manifest or FAILED are the only two outcomes.

#### 5.2 DescribeBackup, ListBackups, DeleteBackup

Served from the catalog index with the legacy fallback. ListBackups implements the full request: `TableName`, `BackupType`, `TimeRangeLowerBound` (inclusive) and `TimeRangeUpperBound` (exclusive), `Limit` (1 to 100, default 100) and `ExclusiveStartBackupArn`, returning `LastEvaluatedBackupArn` when more remain. The order is (`created_at`, `backup_id`), a total order ExtendDB chooses (DynamoDB documents none); the cursor ARN is parsed to its id and the page starts strictly after that pair even when the row no longer exists. The current handler reads only `TableName`; "request and response shapes unchanged" is only true once SDK pagination loops work.

DeleteBackup on a CREATING row returns `BackupInUseException`, as on the service; on a row referenced by a RUNNING `restore_jobs` row (which records the backup ARN) likewise; on a DELETING row (a client retrying after an error) it resumes the deletion inline. Otherwise: set the row DELETING (a tombstone sync honours), delete `extenddb-manifest.json` first so the prefix is no longer a complete backup to any reader, then `delete_prefix` for the rest, then set the row DELETED once a `list` of the prefix returns nothing. The last step relies on a strongly consistent listing, which S3 has had since 2020; on an S3-compatible store with eventually consistent listing the row may stay DELETING until a later reconciler cycle, and it never reaches DELETED while an object remains. If any step fails the row stays DELETING and the API returns InternalServerError; the reconciler retries the deletion later. An earlier draft set DELETED first and deleted bytes second, which left two bad states: a crash mid-delete left bytes behind a DELETED row (invisible, leaking), and because S3 prefix deletion is many requests, a surviving manifest could be re-adopted by sync as a new AVAILABLE backup. The request returns the description with BackupStatus DELETED after the row reaches DELETED.

#### 5.3 RestoreTableFromBackup

The request runs steps 1, 2 and 4 and returns CREATING in milliseconds, as DynamoDB does; the job runs steps 3, 5 and 6. The table exists from the response onwards, so no second restore or CreateTable can take the name while files download, but it accepts no reads or writes until every file has verified and loaded.

1. Parse the ARN with `BackupArn` (the account must equal the caller's before any store access) and take a job permit (`LimitExceededException` when none is free, before the manifest is read). Resolve the ARN to a row or, if absent, to the store prefix: a CREATING row returns `BackupInUseException`; a DELETING, DELETED or FAILED row returns `BackupNotFoundException` without reading the store (a DELETING row may still hold a manifest for a moment). Read `extenddb-manifest.sha256` and `extenddb-manifest.json`, verify the sidecar against the manifest bytes, then `format_version`, the ARN and its agreement with `source_table`, and the data-file list rules (`ExtenddbManifest::from_json_bytes`).
2. Validate the target: name free in the account, the target backend supports every feature in `source_table` (vector indexes, table class); refuse before creating anything otherwise.
3. (Job.) Download every data file to the spool (section 7), hashing each through `CompressedHasher` as it arrives and comparing with the manifest's `sha256`, `md5` and `bytes`. A file that verifies gets a `<file>.verified` marker in the spool, written after the file's `fsync` and renamed into place, so a spooled file without its marker (a crash mid-download) is re-downloaded on resume. The spool is per host: the `restore_jobs` row records `spool_host`, and a successor on another host has an empty spool and downloads everything again. On a filesystem store the files are already local and owner-only, so they are verified in place by streaming them through the hasher and no copy is made; a resume re-hashes them in place. A mismatch fails the restore (step 7), naming the file, before any item has been written. Spooling everything before loading is what makes "no item is written before every checksum verifies" true for the second file as well as the first; a design that loaded file by file would already hold file 1's items when file 2 failed.
4. Create the target table and the `restore_jobs` row (RUNNING, with the job's `owner_generation` and `heartbeat_at`; section 4) in one catalog transaction (PostgreSQL and SQLite) or one session transaction (MongoDB), so no crash leaves a CREATING table without a job row. The table is created with `defer_active`, which all three backends already implement privately (`create_table_for_restore` records the source ARN on PostgreSQL and SQLite): base table exists, status CREATING, no writes accepted. If the create fails because another CreateTable or restore took the name between steps 2 and 4, the request returns `ResourceInUseException` as CreateTable does and the job row insert rolls back with it. Return `TableDescription` with TableStatus CREATING. Overrides are applied here (see below). The job holds the same claim as a backup job (5.1 step 3), keyed `restore:<account>/<table>` on PostgreSQL (the lock #384's `try_restore_lock` already takes, same seed), the row itself on MongoDB, and heartbeats on the same timer.
5. (Job, after step 3.) Per data file: decode through `DataFileEntry::decoder` from the spooled or in-place file, validate every item with a strict restore validator (key attributes present with the manifest's types; every `N` value passed through `validate_and_normalize_number`, which enforces the number bounds and rewrites the value to its normalized form before key text is computed or keys are compared; 400 KB item size, nesting depth, attribute-name sizes, non-empty sets; for a key-ordered backup, strictly ascending keys) and fail the restore on the first invalid item (the current ImportTable path skips invalid items and continues, which is wrong for a restore), then write the file through a new storage method `bulk_load(table, items)` that the backend owns. Each backend writes base rows and index rows together and records progress in a way a crash cannot split from the data:
   - PostgreSQL: multi-row INSERT in 500-row batches with index rows inline, one data transaction per file (localhost PostgreSQL 16, 318-byte items: ~45k rows/s, and a transaction per file costs ~1.3x one transaction for the whole restore). The catalog and the data live in different databases, so the per-file progress record is a row in the data database (`restore_progress(table_id, file_index)`, data migration 005, reserved for PR 9a next to the catalog numbers in PR 1 and PR 6), written in the file's own transaction; the catalog job row holds only the terminal status. A file is therefore applied exactly once. `~1.3x` is at the 64 MiB default, about 200k items per file.
   - SQLite: 10k-item batches, each its own transaction so live writers on the instance are not held behind a whole file, in key order when the backup is key-ordered. Catalog and data share the file, so the progress record `(file_index, items_applied)` commits in each batch's transaction; a resume skips `items_applied` items of the file it stopped in and continues, so no item is applied twice and no file is re-applied.
   - MongoDB: `insert_many(ordered=false)` per file, with restore-mode index backfill as today. A 200k-document file is outside what a single multi-document transaction should hold (`transactionLifetimeLimitSeconds`, cache pressure), so the progress record is written after the insert completes and a resumed restore re-applies the one file whose record is missing, ignoring E11000 duplicate-key errors on that file only (any other write error fails the restore). That is safe because the backup is immutable and the target accepts no other writes: re-inserting an existing document changes nothing. Because E11000 is what detects a duplicate between files, the job then checks `countDocuments` against the cumulative `item_count` of the files applied so far and fails the restore on a shortfall (section 1).
   The restored table has no streams and no TTL, so there is nothing to bypass.
6. (Job.) After all files: PostgreSQL and SQLite have populated indexes inline and the table transitions to ACTIVE; MongoDB marks restore backfill pending and the existing worker promotes each index then the table, as today. The ACTIVE flip is conditional on the table still being CREATING as a restore target and on the job's `owner_generation` (#384's PostgreSQL code already conditions it on CREATING), and the same transaction deletes the table's `restore_progress` rows and marks the `restore_jobs` row DONE. DeleteTable on a restore target is allowed: it removes the table and its progress rows, and the job's next conditional write fails, which marks the job FAILED with reason `table_deleted` and stops it. UpdateTable on a CREATING table is refused as today. An earlier draft had all three backends go through a restore-backfill worker; only MongoDB has one, and PostgreSQL's `gsi_pending` is the live-write propagation queue, not a backfill. Building a backfill on the SQL backends would be new machinery with no user-visible benefit.
7. Failure (verification or load): the job marks the `restore_jobs` row FAILED with the reason (conditional on its generation), deletes the partially created table (the existing DeleteTable path, which also removes its progress rows), removes the spool, and logs the reason with the backup ARN. DescribeTable then returns ResourceNotFound. Crash mid-restore: the reconciler claims RUNNING `restore_jobs` rows whose owner is dead (the same per-backend rule as 5.1 step 6, so on MongoDB an instance cannot resume a restore another instance is still heartbeating) and resumes from the recorded progress: files with a `.verified` marker in this host's spool are trusted, every other file is downloaded and verified again, then loading continues from the progress record. A CREATING table marked as a restore target with no job row (cannot happen after step 4, checked anyway) is removed; a job whose store prefix is unreachable fails and cleans up.

Restore overrides. #384 implements `BillingModeOverride` and `ProvisionedThroughputOverride` and refuses `GlobalSecondaryIndexOverride`, `LocalSecondaryIndexOverride`, `SSESpecificationOverride`, `OnDemandThroughputOverride` and vector overrides with a typed ValidationException. The v1 contract: the two implemented overrides, applied at step 4, plus `GlobalSecondaryIndexOverride` and `LocalSecondaryIndexOverride` with DynamoDB's semantics: each element names a source index and must match its `KeySchema` and `Projection` exactly (ValidationException otherwise), the element's `ProvisionedThroughput` is applied, an empty list restores no indexes of that kind, and absence restores all. `SSESpecificationOverride` and `OnDemandThroughputOverride` keep the typed refusal and the differences doc lists them. One test per field, plus the conflicting cases (`PROVISIONED` with no throughput, an override naming an index the source lacks, an override whose key schema differs).

#### 5.4 ExportTableToPointInTime and ImportTable

Export gains the store as a target and uses `open_table_snapshot`, which fixes the inconsistent-snapshot defect (issue #57, PR #80) with the same code. The request's `S3Bucket` and `S3Prefix` are honored when the store is S3 and the bucket matches the configured one (a different bucket is refused with ValidationException naming the configured bucket, since the server holds credentials for one bucket); with a filesystem store the existing path behavior remains. Import gains the same store as a source. The missing sibling operations DescribeExport, ListExports, DescribeImport, ListImports are added over the same job rows so SDK poll loops work (v1gaps-api-fidelity.md gap 6). Export continues to ignore ExportTime and incremental export in v1 and now says so with ValidationException instead of silently ignoring them.

### 6. Point-in-time recovery in v1

- DescribeContinuousBackups returns ContinuousBackupsStatus ENABLED (DynamoDB always reports this) and PointInTimeRecoveryDescription with PointInTimeRecoveryStatus DISABLED and no EarliestRestorableDateTime.
- UpdateContinuousBackups with PointInTimeRecoveryEnabled true returns ContinuousBackupsUnavailableException, the typed DynamoDB exception modeled on that operation. With false it returns the DISABLED description.
- RestoreTableToPointInTime first checks that the source table exists (TableNotFoundException otherwise, as the live service does), then returns PointInTimeRecoveryUnavailableException, the typed exception the service models and returns on that operation (live service message: "Point in time recovery is not enabled for table '<name>'").
- The differences doc gains a row stating PITR is not supported and pointing at on-demand backups.
- The per-backend `describe_continuous_backups`, `update_continuous_backups`, and `restore_table_to_point_in_time` trait methods and their `continuous_backups` catalog columns are removed.

### 7. Configuration

```toml
[backup]
store = "filesystem"                  # "filesystem" | "s3"; filesystem is the default
data_file_target_bytes = 67108864     # 64 MiB uncompressed per data file
heartbeat_interval_secs = 30          # job heartbeat timer (5.1 step 4)
stale_job_after_secs = 3600           # heartbeat age after which a MongoDB job is dead, and the delay before a reconciler deletes a dead job's prefix on every backend
failed_row_retention_secs = 604800    # FAILED tombstones kept for the operator, 7 days
max_concurrent_jobs = 1               # backup and restore jobs running at once; a further CreateBackup or RestoreTableFromBackup is LimitExceeded
spool_path = "<data_dir>/backup-spool" # restore download area for an S3 store; must not be inside the filesystem root

[backup.filesystem]
path = "<data_dir>/backups"           # default when the section is absent

[backup.s3]
bucket = "my-extenddb-backups"        # required when store = "s3"
prefix = "extenddb/"                  # optional
region = "us-east-1"                  # optional; SDK chain otherwise
endpoint = "http://127.0.0.1:9000"    # optional; moto, Garage, LocalStack, or any S3-compatible endpoint
force_path_style = false
upload_part_size_bytes = 8388608
max_concurrent_uploads = 4
```

A missing `[backup]` section, which every existing deployment has, is equivalent to `store = "filesystem"` with `path = <data_dir>/backups`; the server creates that directory `0700` if it is absent, so an upgrade changes nothing an operator must act on. `deny_unknown_fields` applies to every section; the `[backup]` section is modelled as one struct that owns the job knobs and nests the store kinds (`serde(flatten)` would drop `deny_unknown_fields`, so the crate's `BackupStoreConfig` is composed inline, not flattened). `extenddb init` writes the section with the filesystem default and a commented S3 example. The startup banner prints the backup store kind and root. A filesystem store keeps the same-host failure domain and the deployment guide says so in the first sentence of the backup section, with S3 as the production recommendation.

Memory per running job, which operators size hosts from: a backup holds `upload_part_size_bytes * max_concurrent_uploads` (32 MiB at the defaults, plus one part being assembled and the SDK's retry copy of each in-flight part) plus the bounded read channel (one fetch of 1000 items) plus the gzip window; it does not grow with `data_file_target_bytes` or with the table. A restore holds one data file's decode buffer (bounded by the 4 MiB line cap) plus one insert batch; it keeps no key set (section 1), so it does not grow with the table either. Each running backup also holds one connection from the PostgreSQL data pool for its duration, and each PostgreSQL job one dedicated claim connection outside the pool; startup refuses `pool_size < max_concurrent_jobs + 10`, naming both numbers (10 is the existing `MIN_POOL_SIZE` floor, which stays the minimum for the catalog pool).

The spool: restores from an S3 store download to `spool_path`, created `0700` with files `0600`; startup refuses a `spool_path` that resolves inside the filesystem store root (the store would list and delete it, and sync would read its first component as an account id). Disk cost: S3 store, the compressed backup size at `spool_path` while a restore runs; filesystem store, none, because files are verified in place (section 5.3 step 3).

`extenddb destroy` removes the catalog and data databases and leaves the backup store untouched: it is the copy that survives destroy. A separate `extenddb backup purge --confirm` deletes `<prefix>/<account>/` for every account in this instance's catalog only, refuses while any row is CREATING or DELETING, prints what it will delete before deleting, and is audit-logged (section 8). It lands in PR 7.

Startup validates the store: filesystem root exists, is a directory owned by the server's uid, grants no permission to group or others, every ancestor is owned by the server's uid or by root and none is writable by others without the sticky bit, and it accepts and syncs a probe file; S3 bucket answers HeadBucket with the configured credentials, and the error distinguishes a missing bucket, a denied one, and one in another region. Failure is a startup error naming the path or bucket, not a runtime surprise at the first CreateBackup. A data directory on a filesystem without Unix permission semantics fails `validate` with the path. `sqlite-memory` builds accept the section but CreateBackup returns the `Unsupported` error from section 3.

Authority: the `[backup]` struct in `crates/server` config (PR 7) and `BackupStoreConfig` in `crates/backup-store`; defaults above are the ones they encode.

### 8. Security

- Credentials for S3 come from the SDK chain; ExtendDB never stores them in its catalog. The deployment guide gives least-privilege bucket policy examples (PutObject, GetObject, DeleteObject, ListBucket, AbortMultipartUpload on the prefix).
- Object keys are prefixed by account id, so a tenant's backups are separable by bucket policy or lifecycle rule. The engine refuses any ARN whose account differs from the caller before touching the store.
- Store keys are validated by the store (no empty component, `.`, `..`, backslash, control character, over 1024 bytes) and the components that form a backup prefix are validated again by `BackupArn` before the key is built; the filesystem store additionally refuses any symlink in a path and requires owner-only write on the root (section 2).
- Checksums on every data file and on the manifest are verified before any item is written (5.3 step 3); the target table exists in CREATING meanwhile and accepts no reads or writes, and a mismatch fails the restore, names the file, and deletes that table. The manifest's `backup_arn` must agree with its `source_table` identity, so a mis-assembled manifest cannot restore one table's items under another's name. The restore item validator rejects items whose keys do not match the manifest's key schema, so a forged data file cannot inject rows that break the primary key invariant.
- Backup contents are plaintext DynamoDB JSON inside gzip. Encryption at rest is the store's responsibility and the docs state it. Bucket versioning and object lock are recommended for ransomware resistance; ExtendDB does not depend on either.
- Management actions (CreateBackup, DeleteBackup, RestoreTableFromBackup, `backup sync`, `backup purge`) are audit-logged with account, ARN, and request id.
- The restore spool holds plaintext items while a restore runs; it is created `0700` with `0600` files, lives outside the store root, and is removed when the job ends.

### 9. Observability

Metrics: `backup_jobs_total{outcome=succeeded|failed|cancelled}`, `backup_job_duration_seconds`, `backup_bytes_uploaded_total`, `restore_jobs_total{outcome}`, `restore_job_duration_seconds`, `backup_snapshot_age_seconds` (gauge while a job runs), `backup_store_errors_total{op}`. Logs: one info line at job start and completion with ARN, item count, bytes, duration; one error line per failure with the reason. The `/health` readiness work from the operations report should include store reachability as a component, not as a hard failure (a backup store outage should not take the data plane out of rotation). `/health` is a static 200 today; the component model is new work in the configuration PR. Metric names are variants of the closed `MetricName` enum in `crates/core/src/metrics`; the existing `WorkerLastSuccess`, `WorkerCycleLatency` and `WorkerErrorCount` are emitted by the backup worker and the reconciler like the other workers.

## Testing summary

- Unit: manifest serde and golden files, key mapping and ARN parsing, store conformance.
- Integration, every backend, every PR: round trip with full configuration preservation, composite keys, GSIs and LSIs, vector indexes where supported, legacy fallback, PITR surface.
- Consistency: concurrent-writer snapshot test on every backend.
- Crash: SIGKILL during upload and during restore, verified by the reconciler tests. These extend the SIGKILL harness the migration tests already use. The restore kill point is after a file's transaction commits and before the next file starts; the backup kill point is between a data file upload and the manifest.
- Distribution matrix for the filesystem default path: unprivileged local launch, the npm launcher, the container image with and without a volume, `sqlite-memory`.
- Cross-backend matrix: nightly.
- Live DynamoDB: Phase 2, measured.
- Performance: backup and restore of a 1M-item table per backend, and of a 1M-item table carrying a vector index on the backends that support one, duration and peak memory recorded as the published RTO baseline; memory must stay flat with table size (streaming, never materializing the table). Index contents are not stored in the backup; every index is rebuilt from the items on restore, so the vector cell measures the dominant restore cost.

## Review checklist for implementation PRs

- No data file is uploaded outside a snapshot; the snapshot is opened before the first read and closed after the last.
- `extenddb-manifest.json` is written last and only after every other object succeeded.
- Every failure path deletes the prefix or leaves it unreachable from List, and the row never says AVAILABLE for an incomplete prefix.
- Restore writes no item before every data file's checksum has verified; a verification failure deletes the CREATING target table, which never accepted a read or a write; the request refuses before creating the table when the target cannot represent the manifest or the key ranges overlap.
- A file's data and its progress record commit in one transaction on PostgreSQL and SQLite (per 10k-item batch on SQLite, with the items-applied count), so no item is applied twice; on MongoDB the progress record follows the insert, re-application of the one unrecorded file is idempotent by duplicate-key suppression (code 11000 only; any other write error fails the restore), and the post-resume document count is checked against the manifest.
- Every status write by a job is conditional on its owner generation, and the reconciler takes the same claim as a worker.
- The ARN is parsed by `BackupArn` once, in the engine, before any catalog or store access; no other code splits ARN strings.
- Account scoping is checked on the ARN before any store access.
- No credential, bucket name with credentials, or presigned URL appears in a log line.
- New workers stop on the shutdown signal within the drain window.
- Tests create composite-key tables, not only hash-only tables.

## Drawbacks

- Backups are asynchronous where the current implementation is synchronous; clients that assumed AVAILABLE on return must poll, which is what they do against DynamoDB.
- Long snapshot transactions on PostgreSQL delay vacuum for the backup duration; MongoDB snapshot windows bound backup duration by server configuration.
- A new dependency on the AWS S3 SDK (43 crates; the license notices are regenerated and checked in with it) and an S3 mock in CI.
- A restore from an S3 store spools the whole compressed backup to local disk before loading any of it.
- One core at full utilization for the duration of a backup on compression; `max_concurrent_jobs` and `spawn_blocking` keep it off the request threads but do not make it free on a 2-vCPU host.
- Two code paths for one release while legacy backups remain readable.

## Alternatives considered

- Per-backend fixes to the existing in-catalog backups. Leaves the failure domain, cross-backend, and catalog-loss problems open. Rejected.
- Backend-native tooling (pg_dump, mongodump, sqlite backup API) documented as the strategy. Cluster-scoped, operator-driven, not per-table, and disconnected from the DynamoDB API. Rejected as the primary path; the manual still mentions it for whole-instance disaster recovery.
- `object_store` crate instead of `aws-sdk-s3`. Smaller and multi-cloud, but a second credential chain implementation for operators to learn. Rejected for v1; the `BackupStore` trait keeps the option open.
- A custom binary format instead of the DynamoDB export layout. Faster to parse, but loses ImportTable compatibility in both directions. Rejected.

## Decisions taken 2026-09-10

1. The filesystem store is the default. Local development and the npm launcher keep working with no configuration; the backup manual states in its first sentence that a filesystem store shares the host's failure domain and recommends S3 for production.
2. The legacy PostgreSQL backup reader recovers sort keys (the column-named-sk defect), so backups taken before this work restore correctly. Fixed in #384 (PR 0).
3. The legacy in-catalog reader ships for one minor release after this work lands, then is removed.
4. MongoDB snapshots read in batches under a snapshot-read-concern session; the server's snapshot history window is documented as an operator setting. The scratch-copy approach is deferred until an operator hits the window.
5. This document lands in the repository as `docs/design/15-backup-restore.md` in the first PR; later PRs reference it instead of opening a separate RFC.
