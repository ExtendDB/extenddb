# Design Spec: Off-Host Backup and Restore for ExtendDB

Status: Draft for maintainer review. Written against main `abf8082f` (which carries PR 0 = #384 as `9d13202`, the Cassandra backend, #338, and the PostgreSQL GSI build, #401) and the open series PR 2 = #396 (this document), PR 3 = #393 (supersedes #336, head `aef17ddd`), PR 4 = #394 (supersedes #337, head `3f7107dc`), PR 5 = #395 (stacked on #394, head `069c4b17`); PR 1 is #335 rebased. The revision log at the end holds the dates of each revision. Target: v1.0.

## Summary

ExtendDB backups today are rows inside the same database that holds the data, in a shape private to each storage backend. This spec replaces that with a single portable backup format written to a configured backup store, either a local directory or an S3 bucket, driven by the engine rather than by each backend. The DynamoDB API contract does not change: CreateBackup, DescribeBackup, ListBackups, DeleteBackup, and RestoreTableFromBackup keep their request and response shapes. Backends gain two obligations, a consistent snapshot iterator over a table and a bulk load into a restore target, and lose the obligation to implement backup storage themselves. The format is the DynamoDB S3 export layout plus one ExtendDB manifest, so a backup restores into any backend, imports into Amazon DynamoDB with ImportTable, and a DynamoDB export restores into ExtendDB.

The spec also settles point-in-time recovery for v1: unsupported, reported honestly, with the format designed so a later change-log archive can add it.

## Motivation

The v1 readiness analysis (v1gaps-backup-dr.md, v1gaps-data-integrity.md) found:

1. Every backup shares the failure domain of its data. Host, disk, or database loss takes the backups with it. No off-host mechanism exists.
2. PostgreSQL backup dropped the sort key of every composite-key table because it checked for a column literally named sk; restore then wedged the table in CREATING. Closed by #384 (PR 0 of this series).
3. SQLite and PostgreSQL restore dropped GSIs, LSIs, throughput, and encryption settings; SQLite silently dropped vector indexes (F-19). Closed by #384 for the in-catalog path (vector indexes are refused rather than restored, a refusal the off-host path lifts, 5.1 step 1; table class is recorded and deliberately not restored, as on the service). The three backends still store three different shapes.
4. Backups cannot cross backends or versions because each backend stores its own shape.
5. Point-in-time recovery reports ENABLED with a 35-day window and can never restore.
6. Export is not a consistent snapshot (issue #57, PR #80 open).
7. Loss of the catalog destroys the ability to find or restore backups.

Three separate per-backend fixes would leave items 1, 4, and 7 open. One engine-owned path with a portable format closes all seven.

## Goals

- Backups survive loss of the ExtendDB host and of the backend database when the store is S3.
- One backup format for all backends; a backup taken on any backend restores on any backend.
- Restore reproduces what Amazon DynamoDB reproduces: items, key schema, attribute definitions, GSIs, LSIs, billing mode and throughput, SSE settings, and the vector index set. Table class, streams settings, TTL, tags, and PITR settings are not restored (a restored table is `STANDARD`), matching DynamoDB and #384 (`table_class_is_not_restored`); the manifest records the class.
- A backup is a consistent snapshot of the table as of one instant.
- CreateBackup and RestoreTableFromBackup are asynchronous with DynamoDB status transitions; a crash mid-operation leaves state a startup reconciler resolves.
- The catalog can be rebuilt from the store.
- Existing API request and response shapes are unchanged.

## Non-goals

- Point-in-time recovery. Phase 3 describes how the format supports it later.
- Cross-account restore. The backup ARN account must equal the caller account, as today. `backup sync --adopt-store` can adopt a bucket written by another catalog (section 4), but every adopted backup stays under the account its ARN names; no request crosses accounts.
- Backup encryption inside ExtendDB. Encryption at rest is the store's job (S3 SSE-S3 or SSE-KMS, filesystem encryption). The spec states this in the deployment guide.
- Scheduled backups. Operators schedule CreateBackup externally in v1. Phase 3 adds a scheduler.
- Multi-instance coordination beyond the per-job claims in 5.1 and the maintenance claim of section 4. Two instances may run jobs concurrently; they may not both own one job. There is no single-instance lease on PostgreSQL or MongoDB (readiness item P0-7 is open) and this design does not add one.
- Two live instances with separate catalogs writing one store root. The tombstone rules of section 4 hold within one catalog, so the root's `extenddb-store.json` names the catalog that owns it and a second catalog finds that store unhealthy and neither writes nor deletes there (section 4); `backup sync --adopt-store` hands a root from one catalog to another, and the previous owner then finds it unhealthy. Instances that share one catalog must share one store root, an S3 bucket and prefix or a shared mount (section 4).

## Detailed design

### 1. Backup format

The format is `crates/core/src/backup_format` (PR 4, #394): its module docs (`mod.rs`, `manifest.rs`, `key_order.rs`, `data_file.rs`, `ddb_export.rs`, `layout.rs`) and `crates/core/testdata/extenddb-manifest/README.md` with its frozen `v1.json` fixtures are the authority for the layout, the manifests, the sidecar, key order, the line cap, the ARN and the evolution rule; this section keeps only the rules later PRs build on.

`extenddb-manifest.json` is written after every data file and both DynamoDB manifests succeed. A prefix without it is an incomplete backup and is invisible to ListBackups after `backup sync`. A prefix with a manifest whose sidecar is missing or does not match is corrupt and is refused by restore and skipped by `backup sync`.

`format_version` is checked before anything else is parsed, so a document from another version is reported as unsupported rather than as a parse error about a member this build does not know; a reader accepts every version from 1 to the one it writes (today only 1) and refuses 0 and any later version.

`item_order` is `key_ordered` or `unordered`. Only hash-only and single-range-key tables can be ordered; PostgreSQL (except a table created before #361, which #395 streams `unordered` with a warning) and SQLite sources write `key_ordered` for those, MongoDB sources and multi-part-key tables write `unordered`; a restore may exploit the flag and must produce the same table either way. `key_ordered` is a promise the writer makes and the reader checks per file: the manifest parser enforces the range rules, and the restore runs #394's per-file key-range check on every file as it streams it (5.3 step 5).

A data file line (one `{"Item": ...}` object and its newline) is at most 32 MiB (`MAX_LINE_BYTES` in #394's `data_file.rs`): the encoder refuses a longer item and the decoder fails on a longer line.

- `vector_indexes` has three states: `null`, the source backend has no vector support (a target with vector support restores the table without vector indexes); `[]`, the source supports vector search and the table had none; non-empty, a target without vector support refuses the restore. Entries are creation specifications, not runtime descriptions.

- A target without vector support refuses a manifest with a non-empty `vector_indexes` with the existing message ("restoring a table with vector indexes is not supported by this storage backend") rather than dropping them. This closes F-19 uniformly, and after PR 9a it is the only vector refusal left on the restore path (5.1 step 1).

`backup_creation_date_time` is the instant `open_table_snapshot` returned, read just after the snapshot pinned, and it is the instant encoded in the backup id: CreateBackup opens the snapshot first (after any wait behind an in-flight UpdateTable), then mints the id from that millisecond (5.1 step 2), so the ARN, the manifest and the catalog's `created_at` carry one time.

A restore rejects a backup whose data files contain the same primary key twice, across files as well as within one. For key-ordered backups the manifest's `key_range` check rejects overlap before any file is downloaded and the per-file key-range check proves the rest, on every target. For unordered backups a plain `INSERT` on PostgreSQL and SQLite fails on a duplicate and so does MongoDB's `_id` unique index (E11000), but a Cassandra write is an upsert and detects nothing, so the general rule is a count: after the last file the restore counts the target's items and requires the count to equal the sum of the manifest's `item_count`; a shortfall is a duplicate and fails the restore.

- Numbers are DynamoDB JSON strings, so the 38-digit precision survives the file. A restore into MongoDB of an `N` sort-key value beyond Decimal128's 34 significant digits fails with ValidationException and the restore reports FAILED (see 5.3); it never rounds. Other `N` values are stored as strings there and keep their 38 digits.

### 2. Backup store abstraction

The store is `crates/backup-store` (PR 3, #393): its README (behaviour, IAM, S3-compatible servers, tests), the module docs of `config.rs` (the `[backup.store]` shape, endpoints, clear text, proxies) and `key.rs` (the key rule), and the `put`, `delete_prefix` and `validate` docs in `lib.rs` are the authority, and the item docs of `fs.rs` and `s3.rs` list the race-only and crash-only paths a caller's author reads before writing against the trait. The crate's `BackupStoreConfig` models the `[backup.store]` table (section 7). `extenddb_backup_store::open(&BackupStoreConfig)` is the constructor the server calls. `validate` is the startup check (section 7).

Three store facts that rules of sections 4 and 5 rest on, and the one method a later PR adds:
- On both stores a put that overlaps a `delete_prefix` covering its key may fail, leaving no partial object, or may succeed and leave its complete object after the deletion returns; the store gives no ordering, so callers do not put under a prefix they are deleting, and the design's protections are the job's heartbeat check before each put (5.1 step 4) and the emptiness check before a tombstone row is removed (section 4). The trait has no single-object delete; `delete_prefix` matches a key equal to the prefix (component-aligned, so a prefix `a/b` does not match a key `a/bc`), and that is how DeleteBackup removes one object (5.2).
- Runtime shutdown sends no abort for a put still in flight, an in-flight `CreateMultipartUpload` included (#393's trait doc): those uploads stay until a `delete_prefix` covering the key sweeps them or the lifecycle rule removes them, so a dropped put future is not enough at shutdown, and the server's shutdown awaits its jobs' failure paths, whose `delete_prefix` sweeps them, within the drain window (5.1 step 6).
- Listing has no delimiter form: `list(prefix)` yields every object under the prefix, so a caller that wants the backup prefixes under a root (`backup sync`) lists every object and derives them.
- `put_if_absent`, which PR 7 adds to the trait and both stores for the store-identity file (section 4), creates the object only if no object is under the key and returns `None`, leaving the existing object untouched, if one is; its per-store mechanics are PR 7's section.

### 3. Storage trait changes

`SnapshotEngine` and `TableSnapshot` are `crates/storage/src/snapshot.rs` and the four `snapshot_engine.rs` files (PR 5, #395); the module docs there carry the per-backend mechanism, `snapshot.rs`'s trait docs state what `description` is and which errors end a stream, and `docs/troubleshooting.md` carries the operator side of the PostgreSQL DeleteTable change. The fetch size of every backend's stream is one shared constant, `extenddb_storage::snapshot::paging::DEFAULT_FETCH_BATCH` (1000), with a `test-hooks` override and a fetch counter the conformance check reads.

- Cassandra: `open_table_snapshot` returns `Unsupported`. Cassandra has no `SnapshotEngine`, so the engine routes CreateBackup there to the legacy create (`LegacyBackupReader::create`, the #384 in-catalog path) whether or not `[backup.store]` is configured, the path every backend takes while no store is configured (section 7); the off-host path is never taken there. That stays until PR 14, by which time either a token-range `SnapshotEngine` with a documented non-point-in-time `SnapshotInfo.kind` (`cassandra_token_scan`) has been accepted as a design change to this section, or Cassandra backups are documented as unavailable. RFC-0003 (backend acceptance criteria) has no backup criterion today; the criterion this trait implies ("a backend that cannot fix an instant across a table returns `Unsupported` rather than a best-effort stream") is to be proposed there in a separate docs change, not in PR 5.

The interfaces later PRs add to `extenddb-storage`, each with its contract; the signatures and the row keys are in the section of the PR that adds them (Phasing):
- `bulk_load(target_table_id, claim, file_index, start_at, items) -> Result<applied>`, a new `StorageEngine` method each backend owns (PR 9a), writes the items of one verified data file from item `start_at` on, and their index rows, into a CREATING restore target, records progress as 5.3 step 5 specifies for the backend under the job's `claim` (so a progress write conditioned on the generation has it) and returns how many items it applied. There is one spelling of that signature; 5.3 step 5 calls it.
- The engine is backend-agnostic (main's `crates/engine` reaches every backend through the `extenddb_storage` traits), and nothing in sections 4 and 5 that touches a catalog row (the claim, the heartbeat, the conditional status writes, the store-scoped listings, the restore job record) can be written in it. `BackupCatalog`, a trait in `extenddb-storage` that PR 6 adds and each backend implements, is how the engine reaches the catalog index of section 4; PRs 8, 9a and 10 add methods to the same trait as their sections need them. Section 4's "Authority" line names this trait beside the engine module that binds it.
- `LegacyBackupReader` is a trait in `extenddb-storage` with `describe`, `list`, `restore` and `delete`, plus `create`, which every backend keeps until PR 14: the engine calls it for CreateBackup when no `[backup.store]` is configured (section 7), logging a deprecation warning that names `[backup.store]` on each call, and on Cassandra always, since it has no `SnapshotEngine` (the decision before PR 14 settles whether that stays), and a legacy create takes a `max_concurrent_jobs` permit like any job, returning `LimitExceededException` when none is free (5.1 step 1), since PR 6 removes the slot semaphores #384's creates wait on; each backend implements it with a frozen copy of its #384 code for reading and decoding the legacy shape (not calls through trait methods later PRs remove), and the engine holds `Option<Arc<dyn LegacyBackupReader>>`. PR 14 removes the trait.

### 4. Catalog index

The invariants and state machines every later PR honours, by lettered part; the schema, the per-backend mechanics and the reconciler's duty list are in the sections of PR 6, PR 8 and PR 10 (Phasing), and the sentences there that state a rule refer back here.

(a) The backup row. The engine keeps a catalog row per backup, in `backup_index` (PR 6's schema), as the fast index for Describe and List, and as the state machine record; `status` is CREATING, AVAILABLE, DELETING, DELETED or FAILED. Status mapping to the API: CREATING and AVAILABLE as themselves; DELETING is reported as DELETED by DescribeBackup and DeleteBackup (a client retrying DeleteBackup sees the terminal status) and is not listed; DELETED and FAILED rows are not described (BackupNotFoundException, which is what the live service returns for a deleted backup) and not listed. FAILED and DELETED rows are tombstones the reconciler owns. Transitions and who performs them: CreateBackup inserts the row CREATING under the job's claim (5.1 step 2); the job writes AVAILABLE after the manifest, or FAILED, each conditional on its generation and on `status = CREATING` (5.1 steps 4, 5); the reconciler resolves a CREATING row whose owner is dead to AVAILABLE if a complete, verified manifest exists in the configured store, else to FAILED, under the same condition (5.1 step 6); DeleteBackup moves an AVAILABLE row to DELETING under the row's lock and to DELETED once the prefix lists empty (5.2); the reconciler finishes a DELETING row, deletes the prefix of a FAILED row once its `heartbeat_at` is older than `stale_job_after_secs` and of a DELETED row that still lists objects, and removes a FAILED or DELETED row once its prefix is empty and its `completed_at` is older than `failed_row_retention_secs`.

(b) The restore job record. The engine keeps one restore job record per restore target, called `restore_jobs` in this document. It is #384's restore registration extended with `status` (RUNNING, FAILED, DONE), `kind` (legacy or manifest), the store it reads, the claim (`owner_generation`, `heartbeat_at`), `spool_host`, per-batch progress, `failure_reason` and `completed_at` (PR 6's schema). Transitions: the request writes the row RUNNING with the target table in one transaction (5.3 step 4); the job marks it DONE with the ACTIVE flip, or FAILED, each conditional on its generation and on RUNNING (5.3 steps 6, 7); the reconciler claims a RUNNING row whose owner is dead and resumes or fails it (5.3 step 7); on MongoDB the job's DONE write precedes the worker's ACTIVE flip and the reconciler leaves such a row alone (5.3 step 6). The record is the table's child (`table_restores` cascades with the table on PostgreSQL and SQLite; it is fields of the table on MongoDB and Cassandra), so it lives exactly as long as the table: a DONE record stays while the table exists, `RestoreSummary` is reported only while the table is CREATING (as main does and `restore_summary_is_reported_only_while_creating` pins), and a FAILED record goes with its table when step 7 deletes it, the failure reported by the job's log line and `restore_jobs_total{outcome="failed"}`.

(c) Store identity and health. Each catalog has a random `catalog_id` (`BackupCatalog::catalog_id`); the store's root carries `extenddb-store.json`, holding a random store id and the `catalog_id` of the catalog that owns the root, and every backup row records the store id in `store_id`; server startup, every sync and every reconciler cycle read the file and check it against the catalog (PR 7's section: how the file is created). The store is unhealthy when the file names another catalog, when its store id differs from the `store_id` of the catalog's rows for the configured `store_kind` and `store_root`, when the catalog has rows for the root and the root has no file, or when those rows carry more than one `store_id` (`BackupCatalog::read_store_ids`, section 3). An unhealthy store is not a startup refusal (section 7): the reason is logged, `/health` reports the store component unhealthy, the operations that touch the store are refused, the reconciler acts on no row of the store, and the check runs again each reconciler cycle; a root whose file names another catalog stays unhealthy until an operator adopts it with `backup sync --adopt-store` (PR 10), and the previous owner then finds the store unhealthy and stops acting on it. Instances that share a catalog must share one store root (an S3 bucket and prefix or a shared mount): host-local roots at one path would give each instance different bytes under one `store_root`, so startup and each reconciler cycle also probe the root independently of the host, `head`ing the manifest of the most recent AVAILABLE row and marking the store unhealthy if it is absent. Every duty that reads or writes a backup row acts only on rows of the configured store (`store_kind`, `store_root` and `store_id`), as sync does, the legacy duty excepted: a CREATING or DELETING row of another store is reported and left alone (`backup sync --move-store`, PR 10, resolves it), a FAILED or DELETED row of another store is never removed and its prefix never deleted, and the emptiness check before a row is removed looks in the configured store, which is also what finds an object left by a put that overlapped the prefix's deletion (section 2); so pointing the configuration at a copy of a store never deletes the copy, and no row is resolved against a store that does not hold its bytes.

(d) Identities. The ARN encodes partition, region, account, table, and backup id, and the key prefix is derived from account, table and id deterministically by `BackupArn::store_prefix`, under the configured store's prefix, and no row stores it, so restore, sync, purge and the reconciler derive it the same way and `describe_backup(arn)` works from the store alone after a sync. The engine, the writer and sync all parse and format ARNs through one implementation, `BackupArn` in `extenddb_core::backup_format` (#394); the engine keeps #384's region handling: it resolves a backup under the ARN as written and under the ARN re-spelled in its own region, and refuses a partition other than its own. `backup_creation_date_time` and `created_at` are the id's instant, so the ARN, the manifest, the API's reported time and the ListBackups cursor agree by construction. One row is addressed by `BackupKey` (`account_id`, `backup_id`, `backup_arn`): PostgreSQL, SQLite and MongoDB key `backup_index` by (`account_id`, `backup_id`), Cassandra keys `backups_by_arn` by (`account_id`, `backup_arn`); no method takes a bare backup id, and the engine treats a row whose `account_id`, `table_name` or `backup_arn` (after that re-spelling) differs from the request's as absent. One target is addressed by `RestoreTargetKey` (`account_id`, `table_name`, `table_id`), the table id guarding against a table re-created under the name.

(e) The claim. There is no single-instance lease on PostgreSQL or MongoDB, so each job holds a claim that both excludes a second owner and lets a successor detect a dead one. Every backend sets `owner_generation` (a fresh random value) at claim time, and every catalog write by the job is `WHERE owner_generation = $gen`, so a job that lost its claim cannot publish over a successor's work. No row ever exists unowned: on every backend the claim precedes the row's insert or is the insert itself (5.1 step 2); what the claim is per backend is PR 6's section. Who is dead: on SQLite every CREATING row at startup, and at runtime a row whose in-process slot no task holds; on PostgreSQL a row whose advisory lock is free; on MongoDB and Cassandra a row whose `heartbeat_at` is older than `stale_job_after_secs` (default 300). Staleness is always measured on the database's clock, never on an application host's. The reconciler takes the same claim as a worker, with a fresh `owner_generation` that fences the dead job's generation out, leaves `heartbeat_at` untouched (a refreshed heartbeat would restart the stale window the prefix deletion waits for), writes AVAILABLE or FAILED at once, both conditioned on `status = CREATING`, and never continues the upload. A job whose conditional write matches no row, or whose claim connection errors, performs no further store or table operation, deletes of a prefix or of a restore target included (5.1 step 5, 5.3 step 7); on PostgreSQL a restore target is resumed or deleted only once the row's `heartbeat_at` is older than `stale_job_after_secs`, since a free advisory lock shows that the owner's catalog session ended, not that its process stopped (5.3 step 7).

(f) The maintenance claim. `backup purge`, `backup remove-target` and `backup sync` with `--move-store`, `--forget-store`, `--forget-backup`, `--prune-missing` or `--adopt-store` change rows or bytes that jobs on any instance may be using, and a job permit (5.1 step 1) is per instance, so these commands take a catalog-level maintenance claim first (PR 10's section: the claim per backend and the SQLite serve lock). Every backup and restore job checks the claim after its own claim and row exist (5.1 step 2, 5.3 step 4) and refuses while it is held; while a claim is held the reconciler runs only the duties that resolve the states the command waits on (DELETING rows, rows whose owner is dead, the FAILED-target duty) and skips every other duty; the command waits until no CREATING backup row with a live owner, no DELETING row of the configured store and no RUNNING `restore_jobs` row remains, and refuses and releases the claim if they have not gone within `2 * stale_job_after_secs`, which it prints; a second maintenance command while one holds the claim fails at once. Because the job checks after its row exists and the command checks rows after its claim exists, one of the two always sees the other.

(g) The store, the rows and sync. The store is the source of truth; the row is a cache. Sync considers only rows of the configured store (`store_kind`, `store_root`, `store_id`); rows for another store are reported, not touched, and `backup sync --forget-store <root>` is the explicit opt-in to drop them: it deletes that root's catalog rows outright, leaving no DELETED tombstone, so no deletion duty ever acts on that store's bytes. Sync reports a row whose manifest is gone and marks it DELETING only with `--prune-missing`; without a resolving option (PR 10) it never modifies CREATING, DELETING, DELETED or FAILED rows nor adopts their prefixes, and it never adopts a prefix without a manifest, one whose sidecar does not match, or one whose listing lacks a data file the manifest lists or holds it at another size. Neither Describe nor Restore reads the store for an ARN that has no row: a backup that exists only in the store is BackupNotFound until `backup sync` adopts it, so these rules are the only path from a prefix to an AVAILABLE row. ListBackups lists rows of another store like any other (the response shape has no marker); Describe of such a row returns it and logs a warning; DeleteBackup and Restore of such a row return a ValidationException saying the backup is in a store other than the configured one, without naming either root. No API error names a store root.

(h) Trust boundary of sync: a principal that can write under an account's prefix can forge a backup for that account. Checksums do not help, they are forgeable by the same principal. The deployment guide states that write access to an account's prefix is backup-administrator authority for that account, and gives per-account IAM prefix policies. A server-side MAC over manifests is not in v1; if hostile writers with bucket access are in scope for a deployment, the operator restricts write access rather than relying on ExtendDB to detect forgeries.

(i) Authority: the catalog migration PR 6 adds (PostgreSQL 005, SQLite schema, the MongoDB `backup_index` collection, `tables` fields and version step, and Cassandra V007, each writing
catalog 0.0.6) <!-- version-literal-ok: the catalog version PR 6 introduces -->

### 5. Operations

Per operation, the contract: the request checks in their order, the error each refusal returns, what the response reports and the ordering rules; the step numbers are kept so the revision log's references resolve. The per-backend mechanics, the pipeline and the measurements are in the sections of PR 6, PR 8, PR 9a and PR 13 (Phasing).

#### 5.1 CreateBackup

1. Validate the request as #384 does and in its order, every check before the permit: `TableName` resolved (a table ARN is accepted), the table exists and is ACTIVE for the account (`TableNotFoundException`, "Table not found: <name>", otherwise, whether or not a permit is free), the table name fits the store prefix (`BackupArn`: a name over 255 bytes is refused with a ValidationException naming the limit). #384's `refuse_backup_of_vector_table` is not among the off-host path's checks (the manifest records vector indexes, section 1); the engine keeps the refusal in front of `LegacyBackupReader::create`, the path of every backend without `[backup.store]` and of Cassandra always (section 7), and the tests that change are PR 8's and PR 9a's sections. A second CreateBackup on a table that already has a CREATING backup is allowed and takes its own snapshot; the `BackupInUseException` the service models on CreateBackup is not raised. Then reserve a job slot: `max_concurrent_jobs` is a per-instance semaphore the request `try_acquire`s (the maintenance claim of section 4 is the cross-instance exclusion), and the permit lives with the job; if none is free return `LimitExceededException` before opening anything, because a queued snapshot would hold a PostgreSQL transaction or a MongoDB snapshot session while it waited; RestoreTableFromBackup and the legacy create take a permit from the same semaphore and return the same error (5.3 step 1, section 3). The default is 4 (section 7), so one running restore does not turn every other backup operation on the instance into `LimitExceededException`.
2. Open the table snapshot (`SnapshotEngine::open_table_snapshot`) in the request. The pin happens during the request, so the backup holds every write acknowledged before the request was received, which is stricter than the service's one-minute window. Mint the backup id from the millisecond the open returned, just after the pin (`format_backup_id`), and the owner generation, then, through `BackupCatalog::claim_backup` (section 3), insert the catalog row with status CREATING, `created_at` = the id's instant, `owner_generation`, `heartbeat_at` = the database's `now()`, and `source_table_details_json` taken from the snapshot's description; then check the maintenance claim (section 4): if it is held, set the row FAILED with reason `maintenance`, release the snapshot, the lock and the permit, and return `LimitExceededException`; otherwise return `BackupDetails` with BackupStatus CREATING. Everything from the open to the hand-off in step 3 runs in a detached task whose result the request awaits, so a client that disconnects mid-request cannot leave a row whose owner was never spawned; if the row insert fails the snapshot is dropped, the lock released, the permit returned, and nothing was written.
3. The claim: section 4(e) states the rules; what the claim is on each backend, the claim connection's settings and the hand-off to the worker are PR 6's and PR 8's sections.
4. The job streams items from the snapshot into gzip data files through `DataFileEncoder`; a file closes once its `uncompressed_bytes` reaches `data_file_target_bytes` (default 64 MiB), so a file exceeds the knob by less than one line, at most `MAX_LINE_BYTES` (32 MiB, section 1), which is also the knob's minimum. Every item is checked, before it is encoded, with the item validator PR 8 adds to `extenddb-core` (`extenddb_core::validation::validate_restorable_item`, with this instance's `max_item_size_bytes`; the restore binds the same function, 5.3 step 5), so no backup that no restore can load is reported AVAILABLE; that is a regression from main for a table that already holds a value #618 let in (Drawbacks), and the reason reaches the operator only (`backup list --failed` and the log); the client sees CREATING and then BackupNotFound. The heartbeat is written on a timer (`heartbeat_interval_secs`, default 15) for as long as the job task is alive, independent of upload progress; before each put the job checks that its latest heartbeat confirmed the claim within `heartbeat_interval_secs` and starts no put otherwise; a heartbeat that does not confirm the claim, or that has not returned within `heartbeat_interval_secs`, aborts the job without further store writes, deletes included. `stale_job_after_secs` must exceed several heartbeat intervals; startup refuses a value under `3 * heartbeat_interval_secs`, which is what makes that detection precede a reconciler's deletion. After the last file: write `manifest-files.json`, `manifest-summary.json`, `extenddb-manifest.sha256` (the order #394's `BackupDocuments::build` doc gives); re-check the claim; then write `extenddb-manifest.json` and update the row to AVAILABLE with size and count (`JobClaim::set_status(CREATING, AVAILABLE)`, conditional on the generation and on `status = CREATING`). An update whose outcome is unknown is followed by a re-read of the row, not treated as a failure; one that matches zero rows ends the job with no store access. Store writes are not fenced by the generation; the re-check narrows the window in which a fenced-out job can still write a manifest, and the FAILED tombstone (section 4) closes what remains: sync never adopts a prefix whose row is FAILED, and the reconciler never deletes a prefix while the row's `heartbeat_at` is younger than `stale_job_after_secs` on the catalog database's clock, so a late manifest from a fenced-out job lands under a tombstone that sync will not adopt.
5. On any failure, including `SnapshotExpired`: set the row FAILED with the reason, conditional on the generation and on `status = CREATING`, so a job whose AVAILABLE update committed with its response lost cannot turn a backup a client has seen AVAILABLE into a deleted one. Only if that write reports exactly one row matched does the job stop its uploads, await its in-flight puts and `delete_prefix` the partial backup (which on S3 also aborts any upload still open under it); a write that matches zero rows, or any error on the claim connection, ends the job with no further store access of any kind, because the holder of the claim owns the prefix. If the delete fails the reconciler retries it (section 4). A backup never resumes from a cursor position, so a lost snapshot means a new CreateBackup. DescribeBackup returns BackupNotFound; ListBackups omits it.
6. Shutdown: the snapshot lives in the process and dies with it, so a cancelled job can never complete. On cancellation the worker runs step 5 with reason `shutdown`, and the server's shutdown awaits each job's failure path within the drain window before the runtime stops: runtime shutdown sends no abort for a put still in flight (section 2), so step 5's `delete_prefix` is what sweeps its upload. If the catalog is unreachable it leaves the row CREATING for the reconciler; if only the store is unreachable the row is FAILED and the reconciler deletes the prefix later. Crash: on startup and every reconciler cycle, a CREATING row is resolved when its owner is dead, by the test and the claim of section 4(e); the prefix of a FAILED row is deleted only once `heartbeat_at` is older than `stale_job_after_secs`, the delay step 4 relies on. A restarted process cannot finish a CREATING backup; AVAILABLE from an existing manifest or FAILED are the only two outcomes.

#### 5.2 DescribeBackup, ListBackups, DeleteBackup

Served from the catalog index with the legacy fallback. DescribeBackup reads the row by the ARN's account and backup id (`BackupCatalog::read_backup_row`) and returns BackupNotFoundException unless the row's `account_id`, `table_name` and `backup_arn` (after the region re-spelling of section 4) equal the request's, as 5.3 step 1 does. ListBackups implements the full request as #384 implements it (the members, the (`created_at`, `backup_arn`) order and the cursor rules with #384's two exceptions), except that `TableName` may be a table name or a table ARN, as the service accepts it (measured on DynamoDB) and as main's CreateBackup already does; the differences doc's `ListBackups` paging row changes with PR 6 (section 10).
DeleteBackup on a CREATING row returns `BackupInUseException`, as on the service; while the backup is in use likewise; on a DELETING row it resumes the deletion inline; on a DELETED or FAILED row it returns `BackupNotFoundException`, as Restore does; on a row of another store it returns the ValidationException of section 4, and while the configured store is unhealthy, on a row of that store the ValidationException of section 7. A backup is in use while a restore target registered from it is CREATING (`BackupCatalog::backup_in_use`), main's rule on every backend, which 5.3 step 1 applies to a second restore of the backup; the rule reads the target's status, not the job's, so on MongoDB it also covers the window between the job's DONE write and the worker's ACTIVE flip (5.3 step 6). DeleteBackup runs the in-use check and its DELETING write in one transaction under the backup row's lock (`BackupCatalog::start_backup_delete`), and a restore's registration (5.3 step 4) re-checks the in-use rule and `status = AVAILABLE` under the same lock, so the two order wholly one before the other, as on main: a DeleteBackup that wins leaves the registration a row that is not AVAILABLE (`BackupNotFoundException`, no target left), and a registration that wins makes the DeleteBackup return `BackupInUseException`; so no restore loads from a backup a DeleteBackup has started to delete, on any backend. Otherwise: set the row DELETING (a tombstone sync honours), delete `extenddb-manifest.json` first so the prefix is no longer a complete backup to any reader (`delete_prefix` on the manifest's exact key, section 2), then `delete_prefix` for the rest, then set the row DELETED (`set_backup_deleted`) once a `list` of the prefix returns nothing; if any step fails the row stays DELETING and the API returns InternalServerError, and the reconciler finishes the deletion later (section 4). The request returns the description with BackupStatus DELETED after the row reaches DELETED.

#### 5.3 RestoreTableFromBackup

The request runs steps 1, 2 and 4 and returns CREATING in milliseconds plus the manifest parse, as DynamoDB does; the job runs steps 3, 5 and 6. The request's own awaits are the checks of step 1 in their order, the permit, the manifest read and the validation of step 2; the step 4 transaction and the spawn of the job run together in a detached task whose result the request awaits, so a client disconnect cannot commit the table and the RUNNING row without an owner. The table exists from the response onwards, so no second restore or CreateTable can take the name while files download, but it accepts no reads or writes until every file has verified and loaded.

1. Check the request in the order main uses and the differences doc records, every refusal that needs no store access before the permit: the overrides' shape (below); the ARN with `BackupArn` (the account must equal the caller's before any store access); the target name (`TableAlreadyExistsException` when a table of that name exists, `TableInUseException` when it is a CREATING restore target); the backup row, read by the ARN's account and backup id and accepted only when its `account_id`, `table_name` and `backup_arn` (after the region re-spelling of section 4) equal the request's, or, if there is no such row, resolved through the `LegacyBackupReader` (section 3): an ARN with neither is `BackupNotFoundException`, so an ARN of account B that carries the id of account A's backup is BackupNotFound and never A's row, a CREATING row returns `BackupInUseException`, a backup in use (the rule of 5.2) returns `BackupInUseException` naming that table, a DELETING, DELETED or FAILED row returns `BackupNotFoundException`, a row of another store returns the ValidationException of section 4 and a row of an unhealthy configured store the one of section 7, none of them reading the store; then, last, the job permit (`LimitExceededException` when none is free). Only then read `extenddb-manifest.sha256` and `extenddb-manifest.json`, verify the sidecar against the manifest bytes, then `format_version`, the ARN and its agreement with `source_table`, and the data-file list rules (`ExtenddbManifest::from_json_bytes`). A manifest missing behind an AVAILABLE row returns `BackupNotFoundException` and logs the row for `backup sync --prune-missing`.
2. Validate that the target backend supports every feature in `source_table` that a restore reproduces (a non-empty `vector_indexes` into a backend without vector support is the one case, section 1); refuse before creating anything otherwise. Unlike #384 (`ensure_single_part_base_key`), this path restores multi-part-key tables (as `unordered` backups, section 1): `bulk_load` keys each row and derives its index rows with the functions the backend's item write path uses (section 3), so a restored multi-part-key table is laid out as a natively created one.
3. (Job.) Write the verified manifest and sidecar to the spool, then download every data file to the spool (PR 7's section), hashing each as it arrives and comparing with the manifest's `sha256`, `md5` and `bytes`; on a filesystem store the files are verified in place and no copy is made. A transport error during a download is retried with backoff for up to 15 minutes (a constant, not a knob in v1), the row kept RUNNING and heartbeated, before the restore fails (step 7); a checksum or size mismatch is not retried and fails the restore, naming the file, before any item has been written. Spooling everything before loading is what makes "no item is written before every checksum verifies" true for the second file as well as the first. The spool's `.verified` markers, `spool_host` and the resume rules are PR 9a's section.
4. Create the target table and the `restore_jobs` row (RUNNING, with the job's claim, `kind = manifest` and the store the backup row names; section 4) in one catalog transaction (PostgreSQL and SQLite), one session transaction (MongoDB) or, on Cassandra, one `INSERT ... IF NOT EXISTS` of the `tables` row, whose columns are the job row, so no crash leaves a CREATING table without a job row. If another CreateTable or restore took the name between steps 1 and 4, the request returns `TableAlreadyExistsException` (or `TableInUseException` when the winner is itself a CREATING restore target) and the job row insert rolls back with it; CreateTable keeps `ResourceInUseException`. The registration (`BackupCatalog::claim_restore`) re-checks inside its transaction, under the backup row's lock that DeleteBackup's `start_backup_delete` takes (5.2), that the backup row is still AVAILABLE and that no restore target registered from it is CREATING: a row that is no longer AVAILABLE returns `BackupNotFoundException`, a backup in use returns `BackupInUseException`, and no target is left. After the transaction commits the job checks the maintenance claim (section 4); if it is held, the job runs step 7 with reason `maintenance` and the request returns `LimitExceededException`. Otherwise return `TableDescription` with TableStatus CREATING. Overrides are applied here (below). A restore the reconciler resumes is a job and takes a `max_concurrent_jobs` permit like a new one; when none is free the row is skipped until the next cycle.
5. (Job, after step 3.) Per data file: read the verified file through #394's `ExtenddbManifest::reader_prehashed`, apply the per-file key-range check of section 1 when the backup is key-ordered, validate every item with PR 8's item validator with the target's limits and fail the restore on the first invalid item, then write the file through `bulk_load(target_table_id, claim, file_index, start_at, items)` (section 3), with `start_at` the recorded `items_applied` of a file a resume stopped in and 0 otherwise. Each backend writes base rows and index rows together and records progress so that a crash cannot leave an item applied twice: in one transaction with the data on PostgreSQL and SQLite, and by idempotent re-application of the one unrecorded file or batch on MongoDB and Cassandra (PR 9a's section: the batch sizes and progress records). The restored table has no streams and no TTL, so there is nothing to bypass.
6. (Job.) After all files, and for an unordered backup after the count of section 1 matched, the job flips the target to ACTIVE conditional on the table still being CREATING as a restore target and on the job's `owner_generation`; on PostgreSQL and SQLite the table and every index of the target flip in one catalog transaction, which also marks the `restore_jobs` row DONE; on Cassandra the index rows are created ACTIVE with the table and the lightweight transaction on the `tables` row flips the table and marks the job row DONE. A Query on each GSI, and SearchVectors where the target supports it, therefore sees every restored item as soon as the target reports ACTIVE. MongoDB's sequence differs, because the existing backfill worker, not the job, promotes the indexes: the job marks the `restore_jobs` row DONE (conditioned on its generation and on RUNNING) and sets `restore_backfill_pending` in one session transaction, and the job task ends there; the worker promotes each index and then flips the table to ACTIVE, conditioned on `restore_backfill_pending` and on CREATING, not on the job's generation; and the reconciler never treats a row with `restore_backfill_pending` as a dead RUNNING job (the row is DONE). DeleteTable on a restore target is refused with `ResourceInUseException`, as #384 does and as the service does, which is why the job and the reconciler remove a target through `remove_restore_target` (step 7); there is no user-facing way to cancel a running restore. UpdateTable on a CREATING table is refused as today.
7. Failure (verification or load): the job marks the `restore_jobs` row FAILED with the reason, conditional on its generation. Only if that write matched exactly one row does the job remove the partially created table, through `BackupCatalog::remove_restore_target` (section 3), keyed by the target's account, name and table id and conditional on the table still being a CREATING restore target, which also deletes its progress rows, never through the DeleteTable API; a write that matches zero rows ends the job with only its spool removed, because the claim holder owns the table. DescribeTable then returns ResourceNotFound. Crash mid-restore: the reconciler claims RUNNING `restore_jobs` rows whose owner is dead (section 4(e)) and resumes from the recorded progress, reading the store the job row records if it is the configured store, failing the restore and naming `backup sync --move-store` if it is not, and resuming nothing while the configured store is unhealthy; on PostgreSQL only once the row's `heartbeat_at` is older than `stale_job_after_secs`, the delay the prefix deletion already waits, since a free advisory lock shows that the owner's catalog session ended, not that its process stopped, and the restore's data writes carry no generation; the owner aborts at its next heartbeat, inside that window. A legacy RUNNING restore whose owner is dead is marked FAILED and its target removed, never resumed (section 3). Shutdown: a restore job stops at its next batch without writing a status, so step 7 does not run; its row stays RUNNING with its spool and its progress, for a successor once the owner is dead by its backend's rule.

Restore overrides. #384 applies every override the operation models as the service applies it (`crates/engine/src/backup/overrides.rs`) and refuses only `VectorIndexOverride`, which the botocore model this project targets does not carry, with a typed ValidationException. The v1 contract keeps exactly that: the new path applies the overrides at step 4 to the manifest's `source_table` before the target is created, through the same `overrides` module, and `VectorIndexOverride` keeps the refusal. The differences and limits docs' override rows stay as they are.

#### 5.4 ExportTableToPointInTime and ImportTable

Export gains the store as a target and uses `open_table_snapshot`, which fixes the inconsistent-snapshot defect (issue #57, PR #80) with the same code. Exports go under a reserved first-level component at the store root, `<store prefix>exports/<export id>/`, outside every `<account>/` prefix, so `backup sync` skips it, `backup purge` leaves it, and the IAM grant covers it with the rest of the prefix; the request's `S3Bucket` must match the configured bucket (ValidationException naming the configured bucket otherwise), and `S3Prefix` is honoured only under `exports/`. Exporting a table without PITR is an ExtendDB departure from the service, which answers `PointInTimeRecoveryUnavailableException` there; section 10 records it with the Import and Export rows. Import and the sibling describe and list operations are PR 13's section.

### 6. Point-in-time recovery in v1

- DescribeContinuousBackups returns ContinuousBackupsStatus ENABLED (DynamoDB always reports this) and PointInTimeRecoveryDescription with PointInTimeRecoveryStatus DISABLED and no EarliestRestorableDateTime. A missing table is TableNotFoundException ("Table not found: <name>") on all three operations of this section, the exception the service models on each; main maps it to ResourceNotFoundException on the two continuous-backups operations and #335's rebase carries the correction.
- UpdateContinuousBackups with PointInTimeRecoveryEnabled true returns ContinuousBackupsUnavailableException, the typed DynamoDB exception modeled on that operation. With false it returns the DISABLED description. A request without PointInTimeRecoverySpecification, a required member, is a ValidationException (main defaults it to false).
- RestoreTableToPointInTime first checks that the source table exists (TableNotFoundException otherwise, as the live service does), then returns PointInTimeRecoveryUnavailableException, the typed exception the service models and returns on that operation (live service message: "Point in time recovery is not enabled for table '<name>'").
- The differences doc's existing PITR row ("Not supported") is rewritten to point at on-demand backups and name the typed exceptions, including `UpdateContinuousBackups`' `ContinuousBackupsUnavailableException`.
- The per-backend `describe_continuous_backups` and `update_continuous_backups` trait methods and their `continuous_backups` catalog tables are removed (#384 already removed `restore_table_to_point_in_time` from the trait; the engine handler for it returns a ValidationException today and gains the typed exception here).

### 7. Configuration

```toml
[backup]
data_file_target_bytes = 67108864     # uncompressed bytes per data file; a file closes once it reaches this, so it exceeds it by less than one line (5.1 step 4); minimum 32 MiB, the line cap
heartbeat_interval_secs = 15          # job heartbeat timer (5.1 step 4); #384's restore heartbeat interval
stale_job_after_secs = 300            # heartbeat age after which a MongoDB or Cassandra job is dead, and the delay before a reconciler deletes a dead job's prefix on every backend; a new value (#384's restore grace is 60 s)
failed_row_retention_secs = 604800    # FAILED tombstones kept for the operator, 7 days
reconcile_interval_secs = 60          # reconciler cycle (section 4)
max_concurrent_jobs = 4               # backup and restore jobs running at once on this instance, legacy creates and restores included; a further CreateBackup or RestoreTableFromBackup is LimitExceeded
spool_path = "<see below>"            # restore download area for an S3 store; defaults beside the database file on SQLite, required on the other backends
```

`[backup.store]` and its `filesystem` and `s3` tables are the crate's `BackupStoreConfig` (`crates/backup-store/src/config.rs` module doc, #393: the TOML block with every key, its default and `open`'s refusals); `kind = "disabled"`, the per-backend default root, the spool and `backup purge` are PR 7's section.

On SQLite (file-backed) a missing `[backup]` section is equivalent to `kind = "filesystem"` with `path` = `backups/` beside the database file; a `validate` failure of that defaulted root is a logged warning that leaves the store unconfigured, not a startup error, so an upgrade never stops a server that never configured backups, while an explicitly configured root that fails `validate` is still a startup error. On PostgreSQL and MongoDB a missing `[backup.store]` leaves the off-host path unconfigured and startup logs that; `kind = "disabled"` leaves it unconfigured on purpose on any backend. Without a configured store, CreateBackup on every backend uses the legacy in-catalog create (`LegacyBackupReader::create`, section 3) and logs a deprecation warning naming `[backup.store]` on each call, until PR 14 removes that path; after it CreateBackup without a configured store returns a ValidationException naming `[backup.store]`. Legacy backups stay readable, listable, restorable and deletable either way. `sqlite-memory` (any `:memory:` database path) has no database file and so no default root: CreateBackup there takes the off-host path only with `[backup.store]` set and the legacy create without it. Cassandra has no `SnapshotEngine`, so it uses the legacy create even with a store configured (section 3); a configured store serves restores of off-host backups into Cassandra and nothing else there.

Memory per running job, which operators size hosts from: a backup holds the upload window (`upload_part_size_bytes * max_concurrent_uploads` on an S3 store, one write buffer on a filesystem store), the read path, the gzip window and the manifest's data-file entries until the manifest is written; with the byte budget PR 8 adds to the PostgreSQL and SQLite streams (`SNAPSHOT_FETCH_BYTES`, a constant beside `DEFAULT_FETCH_BATCH`, not a `[backup]` key in v1) the read path holds at most one page, the budget plus one row of text, plus its decoded form, and neither term grows with `data_file_target_bytes` or with the table, except on `sqlite-memory`, whose open copies the whole table (section 3). A restore holds one line's decode plus one insert batch plus the parsed manifest for the whole job; neither grows with the table. Each running backup also holds one connection from the PostgreSQL data pool for its duration, and on the separate layout one catalog-pool connection while its snapshot opens (section 3); the backend admits at most half the pool as open snapshots and refuses more with `LimitExceeded`; a running restore holds one data connection and has no slot of its own after PR 6; and each PostgreSQL job holds one dedicated claim connection outside the pool. `pool_size` sizes both pools, and the rule is `pool_size >= max(MIN_POOL_SIZE, 2 * max_concurrent_jobs + 10)`: twice the jobs, so the half-pool bound admits every job `max_concurrent_jobs` allows, plus ten for requests; 18 at the defaults, under the default `pool_size` of 20. It applies whether or not `[backup.store]` is configured, because legacy restores are jobs too. Startup raises a smaller `pool_size` to that value with a warning naming both numbers, as it already raises a `pool_size` under `MIN_POOL_SIZE` (10) today.

A configuration error (a missing or denied bucket, a part size, prefix or key-length problem, an insecure endpoint, a root that fails the owner-only rule) is a startup error naming the path or bucket, except for the defaulted SQLite root above, where it is a warning. A transport failure (no region, no credentials, an unreachable endpoint), and a failure of section 4's identity check or manifest probe, do not stop startup, because a store problem must not take the data plane out of rotation (section 9): the failure is logged with its cause, the store component is reported unhealthy, the operations that touch the store refuse with a ValidationException that names the store's kind and not its root (CreateBackup on the off-host path, and RestoreTableFromBackup and DeleteBackup of an off-host backup; Describe and List, legacy backups and Cassandra's legacy create are unaffected), the reconciler acts on no row of the store (its legacy duty, which touches no store, still runs) and resumes no restore, and the check runs again each reconciler cycle until it passes.

Authority: the `[backup]` struct in `crates/config` (PR 6 adds it with the job keys; PR 7 adds `store` and its validation) and `BackupStoreConfig` in `crates/backup-store`; defaults above are the ones they encode.

### 8. Security

- Credentials for S3 come from the SDK chain; ExtendDB never stores them in its catalog. The least-privilege IAM policy example, the lifecycle rules and the rule that a missing object reads as absent only under `s3:ListBucket` are #393's README ("IAM"); the transport rule (an `http://` endpoint only to loopback or with `allow_insecure_endpoint`, the credential clients' endpoints, proxies disabled for a clear-text endpoint, the `trace` logs) is `config.rs`'s module doc ("Clear text", "Proxies"); the key rule is `key.rs`.
- Object keys are prefixed by account id, so a tenant's backups are separable by bucket policy or lifecycle rule. The engine refuses any ARN whose account differs from the caller before touching the store.
- Checksums on every data file and on the manifest are verified before any item is written (5.3 step 3); the target table exists in CREATING meanwhile and accepts no reads or writes, and a mismatch fails the restore, names the file, and deletes that table. The manifest's `backup_arn` must agree with its `source_table` identity, so a mis-assembled manifest cannot restore one table's items under another's name. The restore item validator rejects items whose keys do not match the manifest's key schema, so a forged data file cannot inject rows that break the primary key invariant.
- Backup contents are plaintext DynamoDB JSON inside gzip. Encryption at rest is the store's responsibility and the docs state it. Bucket versioning and object lock are recommended for ransomware resistance; ExtendDB does not depend on either.
- Management actions (CreateBackup, DeleteBackup, RestoreTableFromBackup, `backup sync`, `backup purge`, `backup remove-target`) are audit-logged with account, ARN, and request id.

### 9. Observability

Metrics: `backup_jobs_total{outcome=succeeded|failed|cancelled}`, `backup_job_duration_seconds`, `backup_bytes_uploaded_total`, `restore_jobs_total{outcome}`, `restore_job_duration_seconds`, `backup_snapshot_age_seconds` (gauge while a job runs), `backup_store_errors_total{op}`. Logs: one info line at job start and completion with ARN, item count, bytes, duration; one error line per failure with the reason. The `/health` readiness work from the operations report should include store reachability as a component, not as a hard failure (a backup store outage should not take the data plane out of rotation). `/health` is a static 200 today; the component model is new work in the configuration PR, and a transport failure of the store, or a failure of its identity check or manifest probe (section 4), marks the component unhealthy rather than stopping the server (section 7). Metric names are variants of the closed `MetricName` enum in `crates/core/src/metrics`; the existing `WorkerLastSuccess`, `WorkerCycleLatency` and `WorkerErrorCount` are emitted by the backup worker and the reconciler like the other workers.

Schema it adds. The `backup_index` row: (the id is `extenddb_core::backup_format::format_backup_id`'s shape; the id and `account_id` are the row's key)
```

account_id, table_name, backup_arn, backup_name,
status            CREATING | AVAILABLE | DELETING | DELETED | FAILED
store_kind        filesystem | s3
store_root        the configured root at creation time: the canonical directory for a filesystem store, `s3://<bucket>/<prefix>` for S3, with `?endpoint=<url>` appended when an endpoint is configured (the URL without userinfo, query or fragment)
```

The backup id has one shape (`01489602797149-73d8d5bc`), minted by `format_backup_id(millis, suffix)` from the snapshot instant (5.1 step 2); #384's `extenddb_storage::util::new_backup_id`, which the legacy in-catalog path calls with the current time, is the same formatter applied to `now()`. The ARN parser accepts the two shapes earlier releases issued (13-digit millis with the hex suffix; 13 bare digits) so legacy backups resolve through the legacy reader; a store prefix carries only the 14-digit shape, because the manifest parser refuses an id that carries no instant to check `backup_creation_date_time` against (#394), so `migrate-legacy` refuses a legacy backup with another id shape (PR 10).

PR 6's migration backfills the new fields on the registrations that exist at migration time, on all four backends: `kind = legacy`, `status = DONE` where the table is not CREATING, and where it is (a restore the upgrade's stop interrupted), `status = RUNNING` with `heartbeat_at` set to the epoch (1970-01-01T00:00:00Z), not NULL, on every backend, so every backend's staleness test selects them (PostgreSQL's test also has an `IS NULL` arm as a second guard, 5.1 step 3), and a sentinel `owner_generation` (0) that no job holds; the first reconciler pass fails those rows as legacy restores (section 3) and removes their targets (`remove_restore_target`), which is what #384's startup sweeps did for such a target.
On Cassandra: On Cassandra the backup row is denormalized into `backups_by_arn`, `backups_by_account` and `backups_by_table`, the three legacy tables reused, with `store_kind IS NOT NULL` marking a new row and `store_kind IS NULL` a legacy one. The two list tables carry no status, so the rule between the three is presence, not status: a `backups_by_account` or `backups_by_table` row exists iff the authoritative `backups_by_arn` row is AVAILABLE. `backups_by_arn` is authoritative and every writer writes it first, so a writer that dies between the writes leaves a state the next sync or reconciler cycle completes; `backups_by_arn` is partitioned by `(account_id, backup_arn)`, so a status-keyed read has no access path in it, and V007 adds `backup_index_by_status`, primary key `((store_root, backup_status), backup_arn)`, one partition per status for a root, which every status write maintains beside the authoritative row.
Versions and the mixed-version rule: MongoDB's expected version is `0.0.2` on main and #384 added its restore fields without a bump; PR 1 leaves MongoDB at `0.0.2`, and PR 6 adds the versioned migration step MongoDB lacks (a `$set` of the version after the collection and field changes, recorded in `schema_history`) and moves it from `0.0.2` to the version the other backends write in PR 6. On PostgreSQL, SQLite and MongoDB it is a new table or collection, `backup_index`, with primary key (`account_id`, `backup_id`) and `backup_id` unique; the legacy `backups` table or collection stays for the `LegacyBackupReader` (section 3), whose queries are scoped to it, so neither reader sees the other's rows. What this leaves is mixed versions on one catalog. A pre-PR-6 server does not read `backup_index`, so it would not list a backup a PR 6 server created, which is the benign direction; the hazard is the reverse: a PR 6 server sees legacy rows only through the frozen reader, so a backup or restore an old server runs during the mixed period is a legacy job whose registration the new server's reconciler does not own (PR 6 replaced #384's sweeps), and a legacy restore the old server abandons is swept by nobody until that server restarts. Section 10 tells operators to stop every pre-PR-6 server before `extenddb migrate`.

Added: `LegacyBackupReader` (section 3 states its contract): the one part that is not frozen is the restore's registration: a legacy restore registers through the `restore_jobs` fields of section 4, with `kind = legacy`, and holds the same claim as a new restore (on Cassandra it also registers in the backup row's `active_restores` map, as every restore there does, section 4, so the frozen DeleteBackup's guard sees it), so the reconciler finds a legacy restore whose owner died as it finds a new one (PR 6 removes #384's per-backend sweeps, and a frozen copy of the registration would be swept by nobody). A legacy RUNNING restore whose owner is dead is marked FAILED and its target removed (`remove_restore_target`, above), as #384's sweep does, and is never resumed: a legacy copy has no data files, spool or progress record to resume from. Cassandra's and SQLite's legacy creates commit a CREATING row before the copy; Cassandra's is the one that needs heartbeating, so it is not frozen either: its insert also sets `owner_generation` and `heartbeat_at`, the engine heartbeats it on the job timer, and the reconciler removes a legacy CREATING row and its `backup_items` through the reader's `delete` once that heartbeat is older than `stale_job_after_secs`; on SQLite, one process, a legacy CREATING row that no running create holds is removed the same way at startup and at runtime; the PostgreSQL and MongoDB legacy creates commit their row AVAILABLE with the copy and leave none. Describe, List, Delete and Restore on the engine consult the new catalog index first and fall back to the reader; List merges the two sources into one (`created_at`, `backup_arn`) order, which works with a bare-ARN cursor because `created_at` is the id's instant on both sides for every id that carries a 14-digit instant (section 4); the two cursor exceptions #384's handler makes are kept (5.2). The frozen reader keeps #384's behaviour for a legacy backup of a table with vector indexes (refused at restore on PostgreSQL, restored without its vector indexes on SQLite, as `docs/differences-from-dynamodb.md` records), and the legacy create keeps main's refusal of such a table, which the engine runs in front of `LegacyBackupReader::create` as main runs it in front of the backend's create (5.1 step 1); only the off-host path backs such tables up and restores them.
What the claim is per backend (4(e) states the rules): PostgreSQL: `pg_try_advisory_lock(hashtextextended('backup:' || backup_id, RESTORE_LOCK_SEED))` on a dedicated, non-pooled connection to the catalog database (outside `pool_size`), taken before the row exists and held for the job's life; the seed is the one constant #384's restore lock already uses, which PR 6 makes `pub` with `#[doc(hidden)]`, so there is one lock key space; the job's heartbeats go through that same connection, so a managed server dropping the idle session surfaces as a failed heartbeat and the job aborts instead of continuing unowned. MongoDB: the row is the claim, born owned by an `update_one` with `upsert: true`, a filter on `owner_generation: {$exists: false}` and an update pipeline that sets the generation and `heartbeat_at: "$$NOW"`, so no row ever exists unowned; a heartbeat that does not return exactly one matched document means the claim may be lost and the job aborts. SQLite: one process, so the claim is an in-process slot; a restart is proof of death, and so is a slot no task holds. Cassandra (a restore target only): the row is the claim, taken with a lightweight transaction `IF owner_generation = <old>` (or `IF NOT EXISTS` at creation), and each heartbeat is a conditional `UPDATE` on the coordinator's clock; a heartbeat whose `[applied]` is false or that errors aborts the job. The lock is PostgreSQL's `FOR UPDATE` on the `backup_index` row, SQLite's write transaction, a write to the backup's `backup_index` document in a MongoDB session transaction (an `$inc` of a counter, so the write always modifies the document and two such transactions conflict), and on Cassandra the lightweight transactions on the `backups_by_arn` row (section 4).

State transitions it owns: AVAILABLE to DELETING and DELETING to DELETED (5.2); a dead legacy restore to FAILED with its target removed, and a dead legacy CREATING row removed (above); the migration's backfill writes DONE or RUNNING with the epoch heartbeat (above).
Documentation rows it corrects: the differences doc's `ListBackups` paging row's statement that the ARN form of `TableName` is refused (accepted from PR 6, as the service accepts it; 5.2); no row changes for DeleteBackup racing a restore of the same backup: the two serialize as on main (5.2). Upgrade manual: stop every pre-PR-6 server before `extenddb migrate`, because an old server neither reads `backup_index` nor marks the rows it writes (section 4); a restore in flight at that stop is failed and its target removed on the first reconciler pass (section 4); and the rollback paragraph inverts: today's manual says a rollback to a pre-upgrade catalog removes every backup created after the upgrade because they lived in the catalog, whereas after PR 6 a catalog restored from a pre-upgrade dump loses the `backup_index` rows while the store keeps the bytes, which the old binary cannot read and `backup sync` re-adopts after the re-upgrade.

The identity file (4(c) states what makes a store unhealthy): On a root with no `extenddb-store.json` and a catalog with no rows for it, the server creates the file with `BackupStore::put_if_absent` (section 2: `If-None-Match: *` on S3, a temporary created `O_CREAT | O_EXCL` and `link`ed to the key on the filesystem store), then reads the file and uses the id it holds. Of two instances of one catalog starting against one empty root, one creates the file and the other's create finds it present, and both use the winner's id. An S3-compatible server that ignores `If-None-Match` on `PutObject` makes the create a plain put, last writer wins: startup's re-read then catches a race lost before it and marks the store unhealthy, naming both ids, and a race lost after it is caught by the next check (a sync, a startup or a reconciler cycle), which finds rows carrying an id the file does not. Startup runs the store's `validate` (its checks are #393's README and `validate` doc) and, on both store kinds, the identity check and the manifest probe of section 4, which run again each reconciler cycle; a root on a filesystem that reports a permissive mode (`0777` from a mount without Unix permission semantics) fails `validate` with the path, and one that reports `0700` while enforcing nothing passes, the case the store cannot observe and the deployment guide names.
The spool: The spool: restores from an S3 store download to `spool_path`, created `0700` with files `0600`. The default is per backend: on file-backed SQLite it is `backup-spool/` beside the database file; on PostgreSQL, MongoDB, Cassandra and `sqlite-memory` with an S3 store `spool_path` is required and startup refuses without it (a filesystem store needs no spool). Startup refuses a `spool_path` that contains or is contained in the filesystem store root (the store would list and delete it, and sync would read its first component as an account id) and one that is or contains the database file's directory, and the reconciler's spool sweep removes only entries whose names match the job-entry pattern (`restore-<table id>`), never other files under `spool_path`. `spool_host` is `<hostname>:<spool_path>`, and startup refuses a `spool_path` whose `.lock` another live instance holds (5.3 step 3). Disk cost of a restore: S3 store, the compressed backup size at `spool_path` while the restore runs; filesystem store, none for the restore, because files are verified in place (section 5.3 step 3). The filesystem store itself holds every backup's compressed size under its root, beside the database on the SQLite default, kept through `extenddb destroy` (below); that is the disk statement a SQLite operator sizes from.

`backup sync` and its options, each with its contract: Sync lists the root (every object, since the trait has no delimiter listing; only the distinct `<account>/<table>/<backup_id>/` prefixes are kept, the reserved `changelog` and `exports/` components skipped), checks each prefix against the catalog as the listing reaches it, reads the manifest and sidecar of the prefixes that have no row, and inserts an AVAILABLE row for each verified manifest whose data files the listing contains, every `data_files` key present with its `bytes`, with an insert-if-absent (`BackupCatalog::insert_backup_row`): a CreateBackup whose row landed between the check and the insert keeps its row and sync skips the prefix. Before adopting, sync parses the manifest's `backup_arn` with the one `BackupArn` type in `extenddb-core` and requires the parsed account, table and backup id to equal the listed path components and the `source_table` identity; a mismatch is logged and skipped. Foreign region or partition in an adopted ARN is accepted and logged; requests check only the account. `--move-store <old root>` re-points the rows of that root to the configured store. It first resolves that root's CREATING and DELETING rows itself, against the configured store: a CREATING row becomes AVAILABLE if a verified manifest is there and FAILED otherwise, and a DELETING row whose prefix there holds no manifest has its deletion finished in the configured store. For each AVAILABLE row it compares the configured store's listing of the row's prefix with the manifest's `data_files` (every key present, with its `bytes`) as well as checking the verified manifest, and stops on a row whose copy is incomplete, naming it; `--forget-backup <arn>` deletes one row's catalog entry so the move can go ahead for the rest; it runs under the maintenance claim like the other commands, refuses a CREATING row with a live owner (the job's next conditional write would match nothing and its manifest would be adopted by the next sync) and a backup in use, one from which a restore target is CREATING, and for a legacy ARN, which has no new-format row, says so and does nothing. One rule covers the three tombstone states: the move refuses to carry a DELETING, DELETED or FAILED row whose prefix in the configured store holds a verified manifest, and names it (that prefix is a backup the operator copied before or during its deletion, not a leftover; `--forget-backup` on the row is the way out). Then it rewrites `store_kind`, `store_root` and `store_id`; the reconciler then cleans the leftovers of the moved tombstones in the configured store. `--move-store` and `--forget-store` match `store_root` exactly as stored, the `?endpoint=` suffix of an S3 root included. A root whose file names another catalog stays unhealthy until an operator adopts it with `backup sync --adopt-store`, which takes the maintenance claim, rewrites the file's owner to this catalog and then syncs, recording the file's store id on the rows it adopts; the previous owner finds the store unhealthy at its next check and stops acting on it. On `sqlite-memory` the catalog, and with it the `catalog_id`, is new at every start, so the server runs a plain `backup sync` itself at startup when a store is configured, which adopts a root whose file names a `sqlite-memory` catalog as `--adopt-store` does, rewriting the file's owner to the new `catalog_id` before it syncs, so the root has one owner at a time there too; a root owned by any other catalog is unhealthy there as anywhere, and the backup CLI commands do not exist there (no file to open), so that startup sync is the only catalog-loss recovery there.
`migrate-legacy`: PR 10 adds `extenddb backup migrate-legacy <arn>|--all`, which streams a legacy backup through the frozen reader's item stream, checking each item with the backup job's item validator (5.1 step 4), into `DataFileEncoder` and the configured store under the legacy backup id, so the ARN survives, with a manifest whose `snapshot.kind` says it is a copy of an in-catalog backup (`legacy_in_catalog`, no marker). Before it inserts the AVAILABLE row or deletes anything it re-reads the manifest it wrote through `ExtenddbManifest::from_json_bytes` and checks that the manifest's item count equals the legacy backup's; only then does it insert the row and delete the legacy rows through the reader's `delete`. It refuses a backup, keeping its legacy rows, deleting the prefix it wrote and naming the reason, when the id carries no instant (the 13-digit and bare shapes, which the manifest parser refuses, section 4), when the validator refuses an item (a value #618 let in, which main's legacy restore copies as stored), and when it cannot state the definition (a pre-0.0.4 SQLite backup recorded no vector state, so `vector_indexes` would be a guess); the way out for such a backup is to restore it through the legacy reader and take a new backup of the restored table, which has a new ARN (section 10).
The maintenance claim per backend and the SQLite serve lock (4(f) states the rules): On PostgreSQL the claim is an advisory lock keyed `hashtextextended('backup-maintenance', RESTORE_LOCK_SEED)`, held exclusively on the command's dedicated connection; a job tests it with `pg_try_advisory_lock_shared` and releases the shared lock at once. On MongoDB it is a document in a `backup_maintenance` collection, claimed and heartbeated like a job row (5.1 step 3) and held while its heartbeat is younger than `stale_job_after_secs`; on Cassandra a `backup_maintenance` row claimed by lightweight transaction with a coordinator-clock heartbeat, read by jobs at `SERIAL`. On SQLite every backup CLI command that writes the catalog takes the database's serve lock, as `destroy` and `migrate` do, so the server must be stopped first and no other claim is needed; with the serve lock held every job owner is dead, so before the wait such a command runs the reconciler's dead-owner resolutions itself (a CREATING backup row to AVAILABLE or FAILED, a RUNNING restore to FAILED with its target removed, a DELETING row finished), and a job the stop interrupted never makes it wait or refuse; `backup list` is a read and runs beside a server.

State transitions it owns: a prefix to an AVAILABLE row (adoption); CREATING or DELETING rows of a moved root resolved by `--move-store`; AVAILABLE to DELETING by `--prune-missing`; rows deleted outright by `--forget-store` and `--forget-backup`; a FAILED restore's CREATING target removed by `remove-target`; legacy rows replaced by an AVAILABLE row by `migrate-legacy`.

## Testing summary

- Unit: manifest serde and golden files, key mapping and ARN parsing, store conformance.
- Integration, every backend, every PR: round trip with full configuration preservation, composite keys, GSIs and LSIs, vector indexes where supported, legacy fallback, PITR surface.
- Consistency: concurrent-writer snapshot test on every backend.
- Crash: SIGKILL during upload and during restore, verified by the reconciler tests. These extend the SIGKILL harness the migration tests already use. Backup kill points: between a data file upload and the manifest; between the manifest put and the AVAILABLE update (the one path to the reconciler's AVAILABLE outcome). Restore kill points: after a file's transaction commits and before the next file starts; MongoDB between `insert_many` and the progress write (the path that exercises E11000 suppression and the count check); Cassandra between a batch's last write and its progress write; SQLite mid-batch; PostgreSQL between the ACTIVE flip and the progress-row deletion; MongoDB between the DONE write (with `restore_backfill_pending`) and the worker's ACTIVE flip, where the reconciler must leave the row alone and the restarted worker must finish; between the FAILED write and the target removal of step 7; a fenced-out restore job that resumes after a successor claimed the row (its FAILED write matches zero rows and the successor's table survives); PostgreSQL, a restore job whose catalog session ended (`pg_terminate_backend` on its claim connection) while its data writes continue: no successor loads into or deletes the target until `heartbeat_at` is stale, and the job aborts at its next heartbeat. DeleteBackup kill points: after the DELETING write; after the manifest delete; after `delete_prefix` and before the DELETED write. Shutdown: SIGTERM during a backup (FAILED, empty prefix, no multipart upload left) and during a restore (row left RUNNING, finished after the restart).

- Cross-backend matrix: nightly.
- Live DynamoDB: Phase 2, measured.

## Review checklist for implementation PRs

- No data file is uploaded outside a snapshot; the snapshot is opened before the first read and closed after the last.
- `extenddb-manifest.json` is written last and only after every other object succeeded.
- Every failure path deletes the prefix or leaves it unreachable from List, and the row never says AVAILABLE for an incomplete prefix.
- Restore writes no item before every data file's checksum has verified; a verification failure deletes the CREATING target table, which never accepted a read or a write; the request refuses before creating the table when the target cannot represent the manifest or the key ranges overlap.
- A file's data and its progress record commit in one transaction on PostgreSQL and SQLite (per 10k-item batch on SQLite, with the items-applied count), so no item is applied twice; on MongoDB the progress record follows the insert, re-application of the one unrecorded file is idempotent by duplicate-key suppression (code 11000 only; any other write error fails the restore), and the post-resume document count is checked against the manifest; on Cassandra the progress record follows each batch under a lightweight transaction and at most one batch is re-applied. A key-ordered restore runs the per-file key-range check on every file, and an unordered one ends with a count of the target equal to the manifest's item count. On PostgreSQL the ACTIVE flip precedes the deletion of progress rows; on MongoDB the job's DONE write and `restore_backfill_pending` are one transaction, and the worker's ACTIVE flip is conditioned on that flag and CREATING, not on the job's generation.
- Every status write by a job is conditional on its owner generation and on the row still being in the job's state (`CREATING` for a backup, `RUNNING` for a restore); a job whose conditional write matches no row, or whose claim connection errors, performs no further store or table operation, deletes (of a prefix or of a restore target) included; the reconciler takes the same claim as a worker and leaves `heartbeat_at` untouched.
- The ARN is parsed by `BackupArn` once, in the engine, before any catalog or store access; no other code splits ARN strings.
- Account scoping is checked on the ARN before any store access, every backup row is read by account and backup id and accepted only when its account, table and ARN equal the request's, and every restore-target method takes the target's account, name and table id.
- The backup job validates every item with `validate_restorable_item` before encoding it, keeps validating after the first refusal, and the restore binds the same function.
- A restore's registration re-checks, under the backup row's lock, that the row is AVAILABLE and not in use, and DeleteBackup's in-use check and DELETING write run in one transaction under the same lock.
- A failed restore's target is removed through `remove_restore_target`, never DeleteTable; on PostgreSQL and SQLite `bulk_load` writes index rows in the batch's transaction, with the base rows, and the ACTIVE flip sets every index of the target ACTIVE.
- No API operation or job touches the store while it is unhealthy, the reconciler acts on no row of the store then (its legacy duty, which touches no store, still runs), and only sync with a resolving option and the health check itself read it.
- No credential, bucket name with credentials, or presigned URL appears in a log line, and no API error names a store root.
- New workers stop on the shutdown signal within the drain window: a backup runs its failure path, which the server's shutdown awaits, and a restore stops with its row left RUNNING.
- Tests create composite-key tables, not only hash-only tables.

## Drawbacks

- Backups are asynchronous where the current implementation is synchronous; clients that assumed AVAILABLE on return must poll, which is what they do against DynamoDB.
- Long snapshot transactions on PostgreSQL delay vacuum for the backup duration; MongoDB snapshot windows bound backup duration by server configuration.
- A new dependency on the AWS S3 SDK (its lock entries pinned to the versions that build on the workspace's 1.88 toolchain, which also holds `crc` at 3.3.0 for the server; the licence notices change when PR 7 links the crate into the server) and an S3 mock in CI.
- A restore from an S3 store spools the whole compressed backup to local disk before loading any of it.
- One core at full utilization for the duration of a backup on compression; `max_concurrent_jobs` and `spawn_blocking` keep it off the request threads but do not make it free on a 2-vCPU host.
- Two code paths for one release while legacy backups remain readable.
- A backup of a table holding an `N` value #618 let in fails on the off-host path, where main backs it up (5.1 step 4).

## Alternatives considered

- Per-backend fixes to the existing in-catalog backups. Leaves the failure domain, cross-backend, and catalog-loss problems open. Rejected.
- Backend-native tooling (pg_dump, mongodump, sqlite backup API) documented as the strategy. Cluster-scoped, operator-driven, not per-table, and disconnected from the DynamoDB API. Rejected as the primary path; the manual still mentions it for whole-instance disaster recovery.
- `object_store` crate instead of `aws-sdk-s3`. Smaller and multi-cloud, but a second credential chain implementation for operators to learn. Rejected for v1; the `BackupStore` trait keeps the option open.
- A custom binary format instead of the DynamoDB export layout. Faster to parse, but loses ImportTable compatibility in both directions. Rejected.

## Decisions taken 2026-09-10

1. The filesystem store is the default. Local development and the npm launcher keep working with no configuration; the backup manual states in its first sentence that a filesystem store shares the host's failure domain and recommends S3 for production.
2. The legacy PostgreSQL backup reader recovers sort keys (the column-named-sk defect), so backups taken before this work restore correctly. Fixed in #384 (PR 0).
3. The legacy in-catalog reader ships for one minor release after this work lands, then is removed.
4. MongoDB snapshots read in batches under a snapshot-read-concern session; the server's snapshot history window is documented as an operator setting. The scratch-copy approach is deferred until an operator hits the window.
5. This document lands in the repository as `docs/design/15-backup-restore.md` in PR 2 of the series (PR 0, #384, and PR 1 precede it); later PRs reference it instead of opening a separate RFC.
